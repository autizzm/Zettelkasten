## Проект Global Payout Engine (B2B FinTech Платформа)

## 🎯 Бизнес-контекст и решаемая «боль»

Проект создавался как B2B SaaS-платформа для международных ИТ-компаний и e-commerce маркетплейсов, нанимающих тысячи удаленных подрядчиков (фрилансеров, курьеров, ИП) по всему миру.

Главная проблема бизнеса: отправить 10 000 транзакций из условных ОАЭ или Кипра в 15 разных стран — это ручной ад. SWIFT-переводы идут днями и сопровождаются огромными комиссиями, а бухгалтерия тонет в генерации закрывающих актов и инвойсов для налоговой.

Наше решение: Система, которая принимает от заказчика один реестр (через API или CSV-файл), автоматически списывает деньги с его B2B-баланса, сама конвертирует фиат в нужную валюту (или стейблкоины USDT/USDC) и мгновенно разносит выплаты по конечным локальным картам или криптокошелькам исполнителей, параллельно генерируя закрывающие документы.

---

## 🏗 Высокоуровневая архитектура (High-Level Architecture)

Мы выбрали микросервисную архитектуру на базе Spring Boot 3.x и Spring Cloud, где взаимодействие между сервисами выстроено асинхронно через Apache Kafka. Система разделена по принципу CQRS (разделение чтения и записи).

```unset
[B2B Клиент] ---> ( API Gateway / mTLS ) ---> [ Kafka: payout-requests ]
                                                    |
         +------------------------------------------+

         |                                          |
         v                                          v
[ Core Ledger Service ]                     [ Spring Batch Service ]
(Event Sourcing / Postgres)                 (Парсинг CSV на 100k строк)

         |                                          |
   (Outbox Pattern)                                 |

         |                                          |
         v                                          v
[ Kafka: payout-ready ] <---------------------------+
         |
         v
[ Payout Gateway Integrator ] (Java 21 / Virtual Threads)
         |
         +---> [ API Банков / OTC-Провайдеров ] ---> [ Исполнитель ]
         |
         v
[ Document Service ] (Генерация PDF-актов в S3)
         |
         v
[ Telegram Bot WebApp ] (Уведомления и личный кабинет)
```

## 🛠 Ключевые архитектурные решения и технический дизайн

## 1. Сердце системы: Core Ledger & Гибридный Event Sourcing

Чтобы гарантировать 100% точность балансов, мы отказались от банального апдейта колонок в базе. Мы внедрили Event Sourcing для хранения истории и CQRS для быстрого чтения.

- Source of Truth (База Записи): Таблица `account_events`. Любое движение денег — это append-only запись события (`MONEY_RESERVED`, `PAYOUT_CONFIRMED`). Изменять или удалять строки здесь физически запрещено.
- Read-Model (База Чтения): Таблица `accounts`, где хранится текущий кэшированный баланс. Она нужна исключительно для моментальной проверки `if (balance >= payout_amount)` при старте транзакции.
- Восстановление состояния Aggregat-а: При инициализации кошелька мы вычитываем цепочку событий из `account_events`. Чтобы не читать миллион строк из прошлого, каждые 10 000 событий мы пишем Snapshot (срез состояния) в Redis. При восстановлении объект собирается по схеме: _Последний Snapshot из Redis + только новые события из Postgres, созданные после него_.

## 2. Конкурентные выплаты и изоляция транзакций

Представим кейс: на балансе клиента лежит $100. Ему одновременно прилетает два запроса на выплату по $80.

- Решение: Мы использовали уровень изоляции транзакций `REPEATABLE READ` в PostgreSQL в связке с оптимистической блокировкой (`@Version` в Spring Data JPA).
- Как это работает в коде: Поток А и Поток Б одновременно читают баланс ($100, `version = 5`). Оба видят, что $80 <= $100, и апрувят списание. Поток А первый делает коммит. Hibernate отправляет в базу: `UPDATE accounts SET balance = 20, version = 6 WHERE id = :id AND version = 5`. Строка обновлена. Поток Б пытается сделать то же самое, но условие `WHERE version = 5` больше не выполняется (версия уже 6). База возвращает 0 обновленных строк, а Spring выбрасывает `OptimisticLockingFailureException`. Транзакция Потока Б откатывается, деньги спасены.

## 3. Гарантия доставки сообщений: Transactional Outbox

Если мы спишем деньги в базе, но сервер моргнет до того, как отправит событие в Kafka, система синхронизации сломается.

- Решение: Внедрен паттерн Transactional Outbox. В рамках одной транзакции базы данных `@Transactional` мы сохраняем изменения в таблицы бизнес-логики и одновременно пишем JSON-событие в техническую таблицу `outbox_events`.
- Доставка: Инструмент Debezium (Kafka Connect) непрерывно слушает системный лог записи PostgreSQL (WAL) и автоматически стримит строки из `outbox_events` в топики Kafka. Если наше Java-приложение упадет, Debezium, развернутый независимо в Kubernetes, всё равно гарантированно доставит событие в брокер.

## 4. Интеграция с банками и крипто-провайдерами

Для трансграничных переводов мы построили гибридную модель: фиатные банковские API + регулируемые институциональные крипто-посредники (такие как _BVNK_ или _Stripe Crypto_).

- Интеграция: Для нашего микросервиса `Payout Gateway Integrator` нет разницы между банком и крипто-провайдером — оба обернуты в REST/SOAP адаптеры. Заказчик заводит на платформу фиат (USD/EUR), провайдер по API конвертирует его в стейблкоины (USDT / USDC), а наш сервис через API провайдера распределяет их по кошелькам исполнителей (или через P2P-шлюзы отправляет в виде локальной валюты на карты фрилансеров).
- Использование возможностей Java 21: Сетевые вызовы к внешним API мы завернули в Virtual Threads (Project Loom). Так как банковские API медленные, классический подход «один поток на запрос» быстро забил бы всю память ОС. Виртуальные потоки блокируются на время ожидания ввода-вывода (I/O), не утилизируя реальные потоки процессора, что позволило держать тысячи параллельных HTTP-соединений на скромном железе.

## 5. Стратегия обработки ошибок при таймаутах (Bank Timeout)

Если мы отправили запрос на выплату $500 в банк, но поймали `ReadTimeoutException` (сеть оборвалась, ответа нет) — мы НЕ имеем права делать повторный Retry POST-запроса. Это прямая дорога к двойному списанию денег.

- Наш алгоритм:
    
    1. Переводим статус платежа в промежуточное состояние `UNKNOWN` (или `PENDING_ENQUIRY`).
    2. Включаем Circuit Breaker (Resilience4j), но настраиваем его исключительно на метод Status Inquiry (запрос статуса транзакции).
    3. Раз в 30 секунд асинхронно шлем GET-запрос в банк с уникальным ID платежа, спрашивая: _«Дошел ли до вас платеж №123?»_.
    4. Если банк отвечает `SUCCESS` — закрываем транзакцию в плюс. Если банк отвечает `NOT_FOUND` — мы выдерживаем "cool-down" период (10 минут, чтобы исключить застревание платежа в буфере банка) и только потом безопасно отправляем платеж повторно.
    

## 6. Идемпотентность на всех уровнях

Защита от ситуации, когда бухгалтер дважды кликнул на кнопку отправки из-за лагов UI.

- Ключ идемпотентности: На фронтенде генерируется UUID (`client_id` + `внутренний_id_ордера_в_их_CRM`).
- Слои защиты:
    
    - _Первый рубеж:_ Redis на уровне API Gateway. Пытаемся сделать атомарный `SET key "PROCESSING" NX EX 60`. Если ключ уже есть — возвращаем клиенту `425 Too Early`.
    - _Второй рубеж:_ Уникальный индекс (`UNIQUE CONSTRAINT`) по полю `idempotency_key` в таблице `payouts` в PostgreSQL. Если два запроса проскочат Redis, база выбросит `UniqueViolationException`. Мы перехватим его и вернем клиенту готовый статус ранее созданного платежа.
    

## 7. Пакетная обработка тяжелых файлов (CSV на 100 000 строк)

Загрузка файла такого объема в память гарантированно убьет Java-процесс через `OutOfMemoryError`.

- Решение: Использование Spring Batch со стриминговым чтением.
- Потоковый Flow: API Gateway принимает файл, не читая его, сразу перенаправляет байты в S3-хранилище (MinIO) и возвращает клиенту ID таски (`202 Accepted`). Сервис воркера скачивает файл и с помощью `FlatFileItemReader` читает его построчно, удерживая в памяти фиксированный чанк (пакет) из 1000 строк. Валидные строки пакуются и отправляются в Kafka, а ошибочные (например, некорректный IBAN) — отправляются в skip-лог. Бухгалтер видит прогресс-бар в реальном времени, а система не расходует лишнюю RAM.

## 📊 Масштаб проекта (Production Scale)

Чтобы понимать реальную нагрузку, которой оперирует система:

- Трафик: В среднем от 15 000 до 30 000 выплат в сутки. Пиковые нагрузки приходятся на 1-е и 15-е числа месяца, когда TPS (число транзакций в секунду) достигает 150 выплат/сек.
- База данных: Размер PostgreSQL составляет порядка 150 ГБ рабочих данных. Для удержания высокой скорости запросов таблицы партиционированы по композитному ключу `(month, region)`. Это позволяет делать операцию очистки старых логов (Reconciliation) простым удалением партиции (`DROP PARTITION`), что гораздо быстрее и дешевле для диска, чем тяжелый `DELETE WHERE date < X`.

## 🚨 Реальный Production Incident (Что пришлось расследовать)

На одном из собеседований меня спросили про самый запоминающийся баг, который я чинил в этой системе.

Инцидент: В день массовых выплат клиенты начали жаловаться, что их исполнители получили по две одинаковые выплаты на свои карты, хотя с B2B-баланса в нашей системе списание произошло единожды.

Расследование: Логи нашего Core Ledger были идеальны — списания чистые, дублирования в Kafka нет. Мы полезли в логи `Payout Gateway Integrator` (модуля связи с банком) и увидели массовые `ReadTimeoutException` от конкретного банка-партнера. Банк под нагрузкой обрабатывал запрос дольше наших дефолтных 15 секунд.

Наш Circuit Breaker фиксировал таймаут, переводил статус в `UNKNOWN` и запрашивал статус транзакции через Get Status API банка. Корень проблемы крылся на стороне банка: из-за бага в их внутренней архитектуре в первые 2 минуты после таймаута их API возвращало на наш запрос статуса ответ: `TRANSACTION_NOT_FOUND`. Наша система, доверяя банку, считала, что платеж не прошел, и делала автоматический Retry POST-запроса. Но, как выяснилось, банк _не поддерживал идемпотентность для запросов, которые еще "висели" у них в очереди на обработку_. Они просто создавали второй платеж-дубль.

Как починили: Мы увеличили `ReadTimeout` для этого шлюза до 30 секунд. В коде обработки статуса `NOT_FOUND` мы внедрили "cool-down" таймер на 10 минут. Теперь система ждет, пока буфер банка гарантированно очистится или транзакция упадет в финальный статус, и только после повторного подтверждения принимает решение о ретрае.
