# Batching and Compression - Kafka


![[Pasted image 20260708101450.png]]

Перед отправкой сообщения на Producer собираются в batch:
	- `batch.size` = 16kb (by default) - размер батча (пихает в батч сообщения, пока не наберётся >= `batch.size`)
	- `linger.ms` = 5ms (by default) - интервал, через который автоматически будет закрыт batch. (Даже если не набрался нужный размер)


**Persistence на диск - асинхронно:**

Что происходит при получении сообщения Producer'ом

1. Producer отправляет сообщение лидеру партиции.
2. Broker добавляет сообщение в **append-only log** (в память ОС — **page cache**).
3. Сообщение **сразу становится доступным для чтения** Consumer'ам.
4. Лишь позже операционная система **асинхронно сбрасывает** данные из page cache на физический диск (`fsync` происходит не для каждого сообщения).

То есть сообщение действительно **может быть прочитано до того, как окажется физически записанным на диск**.


> [!warning]
> Если мы устанавливаем сжатие сообщений, то сообщения не будут сжиматься по одному. 
На Producer будет сжат весь batch в  один **RecordBatch**.У **RecordBatch** есть собственный заголовок (batch header), который общий для всего batch: базовый offset, magic version, compression codec, CRC и т.д. Но **каждое сообщение внутри batch по-прежнему имеет свои собственные поля**, включая:
>	
>- key;
>- value;
>- timestamp;
>- headers (Kafka headers);
>- offset delta и др.
>	
> Прочитаны они тоже будут все вместе одним batch и разархивируются только на consumer
> (каждый `poll()` не делает запрос к брокеру на получение нового сообщения, аа достаёт сообщение из прочитанного (и разархивированного в данном случае) batch)

### А что насчет `.log`?

Здесь важно различать логический и физический смысл.

Сообщение **сразу добавляется в лог Kafka** (append к сегменту `.log`), но фактически запись обычно попадает сначала в **page cache**, а не на магнитный/SSD-носитель. Для приложения это выглядит как успешная запись в файл, хотя физический носитель еще не обновлен.



### Процесс отправки сообщения

1. Запрашивает метаданные у KRaft Controller: список топиков, их расположение (где какие партиции, где какие лидеры, в какой конкретно хост ходить)
2. Сериализует сообщение (byte array, json, protobuf)
3. Определяет, в какую партицию будет отправлять сообщения.
   Алгоритмы для выбора партиции:
	-  Explicit partition
	- Roud-robin
	- Key-defined
	- Sticky partitioner
4. Сжатие данных
   Алгоритмы сжатия (compression.codec):
	   - none
	   - GZip
	   - Snappy
	   - LZip4
	   - ZipSTD
5. Создания батча (группировка нескольких сообщений) для уменьшения накладных расходов отправки
	- `batch.size` = 16kb (by default) - размер батча (пихает в батч сообщения, пока не наберётся >= `batch.size`)
	- `linger.ms` = 5ms (by default) - интервал, через который автоматически будет закрыт batch. (Даже если не набрался нужный размер)
	
> **NB!** Если сообщение очень больше (> `batch.size`, оно может быть отправлено сразу - без создания batch.
