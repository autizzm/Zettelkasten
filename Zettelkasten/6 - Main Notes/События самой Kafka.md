# События самой Kafka


> [!note]
> Если приложение не хранит состояние и просто коммитит оффсеты вручную, то смысла особо обрабатывать эти события - нет. Они нужны скорее для очистки состояния, кэшей, соединений.

**~={red}?!=~** Есть один случай, когда `onPartitionsRevoked()` может быть полезен даже без состояния.

Если обработка сообщения может длиться долго (десятки секунд или минуты), некоторые приложения используют `onPartitionsRevoked()` как сигнал:

> "Нам скоро заберут партицию, не начинай обработку новых сообщений, постарайся быстрее завершить текущие."


---

### `onPartitionsRevokedBeforeCommit()`

- закончить обработку сообщений;
- flush локального состояния;
- сохранить дополнительное состояние (если оно не хранится в Kafka).

### Автоматический commit Spring

### `onPartitionsRevokedAfterCommit()`

- очистить кэши;
- закрыть файловые дескрипторы;
- закрыть соединения;
- удалить локальные структуры данных.

### `onPartitionsAssigned()`

- восстановить состояние;
- при необходимости выполнить `seek()`;
- заново создать кэши.

### `onPartitionsLost()`

- только освободить ресурсы и зафиксировать факт потери партиций в логах или метриках.


---
~={pink}**А почему нельзя коммит оффсета сделать в той же транзакции, что и запись в БД. Так ведь проще. Если в БД записалось корректно, то дойдем до коммита оффсета и завершим транзакцию, если упали после записи в БД, не дойдя до коммита оффсета - транзакция в БД откаттится.**=~

Вот так
```java
@Transactional
public void listen(...) {

    paymentRepository.save(...);

    ack.acknowledge();
}
```

**Что будет, если после commit offset упадёт БД?**

Представим такую последовательность:

```
BEGIN DB

↓

UPDATE payment

↓

OffsetCommitRequest → Kafka OK

↓

COMMIT DB

↓

DB crash
```

Получили:

```
Kafka offset   ✅
DB             ❌
```

Сообщение больше никогда не будет прочитано.

Но изменения в БД потеряны.
