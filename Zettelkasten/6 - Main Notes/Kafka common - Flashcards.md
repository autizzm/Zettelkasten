Q: В чём разница между retention и log compaction в Kafka и когда что использовать?  
A: **Retention** — это временной лимит хранения сообщений в партиции (по времени или размеру). Сообщения удаляются, когда истекает `retention.ms` (например, 7 дней) или `retention.bytes` (например, 10 ГБ). Подходит для event streaming, где важны все события за период (клики, логи, транзакции).  
	  
**Log compaction** — это режим, при котором Kafka хранит **только последнее сообщение для каждого ключа**, удаляя старые дубли. Сообщения не удаляются по времени, а «сжимаются» до уникальных ключей. Требует `cleanup.policy=compact` и наличия ключей у сообщений. Подходит для storage use-case: кэш состояний (профиль пользователя, баланс счёта, конфигурация), где важно только текущее значение per key.  
	  
**Комбинированный режим** (`cleanup.policy=compact,delete`) — сообщения сохраняются и по retention, и compact: старые дубли удаляются, но сообщения старше retention тоже. Используется, когда нужно хранить последние значения, но с ограничением по времени (например, состояние с TTL).  
	  
segment  - активный файл, куда пишутся сообщения:
	
```
orders-0/
├── 00000000000000000000.log
├── 00000000000000000000.index
├── 00000000000000000000.timeindex
├── 00000000000001048576.log
├── 00000000000001048576.index
├── 00000000000001048576.timeindex
└── ...
```
	
Каждый `.log` — это один сегмент. Имя файла — это base offset первого сообщения в сегменте.
	
Например:
	
- `00000000000000000000.log` — сообщения с offset 0+
    
- `00000000000001048576.log` — сообщения с offset 1,048,576+
	
- `segment.ms` - Максимальное время жизни активного сегмента до его принудительного закрытия.
- `segment.bytes` - Максимальный размер сегмента.
	  
---  
**По умолчанию**  
- cleanup.policy=delete  
- retention.ms=604800000 (7 дней)  
- retention.bytes=-1 (не ограничено по размеру)  
- segment.ms=604800000 (7 дней)  
- segment.bytes= ... 1GiB

Q: Как Kafka узнает, жив ли consumer?
A: 2 способа, работают параллельно:  
Два разных таймаута в Kafka Consumer  
1. session.timeout.ms + Heartbeat (отдельный поток)  
Назначение: обнаружение падений приложения или сетевых проблем.  
Как работает: внутренний heartbeat-поток (background thread) отправляет heartbeat-запросы на Group Coordinator каждые heartbeat.interval.ms (по умолчанию 3 сек).  
Если heartbeat не приходит дольше session.timeout.ms (по умолчанию 45 сек в Kafka 3.0+) — консьюмер считается мёртвым, запускается ребаланс.  
Не зависит от poll() — heartbeat работает даже если приложение застряло в обработке.
2. max.poll.interval.ms (ограничение между вызовами poll())  
Назначение: обнаружение «зависших» консьюмеров, которые технически живы (heartbeat шлют), но не обрабатывают сообщения (livelock).  
Как работает: если приложение не вызывает poll() дольше max.poll.interval.ms (по умолчанию 5 минут) — консьюмер исключается из группы, даже если heartbeat шлёт.  
Почему это важно: без этого консьюмер мог бы держать партиции, но не реально не потреблять (например, вечный цикл в обработке, deadlock).

Q: Расскажи о том, как организовано хранение сообщений в Kafka (по файлам)
A: Внутри директории партиции находятся следующие файлы:
1. .log — основной файл сообщений  
Содержит непосредственно сообщения в бинарном формате (ключ + значение + метаданные).  
Сообщения записываются последовательно (append-only log).  
Пример имени: 00000000000000000000.log (начальный оффсет в имени).
2. .index — индексный файл  
Содержит маппинг оффсетов на позиции в .log файле.  
Позволяет быстро находить сообщение по оффсету без линейного сканирования.  
Пример: 00000000000000000000.index.  
3. .timeindex — временной индекс  
Содержит маппинг timestamp → позиция в .log.  
Используется для поиска сообщений по времени (time-based retention, поиск по времени).  
Пример: 00000000000000000000.timeindex.  
4. .snapshot — снапшот оффсетов (для consumer groups)  
Хранит закоммиченные оффсеты консьюмеров (в __consumer_offsets топике).  
Используется для быстрого восстановления состояния consumer group
	
```
orders-0/
├── 00000000000000000000.log
├── 00000000000000000000.index
├── 00000000000000000000.timeindex
├── 00000000000001048576.log
├── 00000000000001048576.index
├── 00000000000001048576.timeindex
└── ...
```
	
Каждый `.log` — это один сегмент. Имя файла — это base offset первого сообщения в сегменте.
	
Например:
	
- `00000000000000000000.log` — сообщения с offset 0+
    
- `00000000000001048576.log` — сообщения с offset 1,048,576+

Q: Расскажи о том, что такое unclean leader election. Зачем это нужно/не нужно. Как настраивается.
A: `unclean.leader.election` — это настройка Kafka, которая определяет, можно ли выбрать лидером реплики, которая не успела полностью синхронизироваться с предыдущим лидером.
	
Это одна из самых важных настроек, связанных с компромиссом между доступностью (availability) и сохранностью данных (durability).
	
**Если unclean.leader.election=false (по умолчанию)**
	
Kafka не разрешает выбирать лидером реплику вне ISR.
	
Результат:
	
- partition становится offline;
    
- producers не могут писать;
    
- consumers не могут читать (для этой partition);
    
- Kafka ждёт возвращения одной из ISR-реплик.
    
**Плюс:**  данные не теряются.
    
**Минус:**  partition недоступна.

Q: Для чего нужна настройка `min.insync.replicas`?
A: `min.insync.replicas` — это минимальное число синхронных реплик (включая лидера), необходимое для успешной записи при `acks=all`
	
Например, если текущее количестов ISR = 1, но `min.insync.replicas = 2`. То Kafka откажет в записи.
	
Producer получит ошибку:
	
- `NotEnoughReplicas`
    
- или `NotEnoughReplicasAfterAppend`
    
То есть Kafka предпочитает не принимать запись, чем принимать её с недостаточной репликацией.
	
**Самое важное: работает только с `acks=all`**

Q: Как Kafka восстанавливается при падении ISR, если текущее количество ISR меньше `min.insync.replicas`? Приводит ли она follower replica в синхронное состояние? Или просто ждет пока не поднимется ISR?
A: Kafka активно приводит follower в синхронное состояние через обычный механизм репликации.
	
Как только follower догонит лидера настолько, что будет удовлетворять критериям ISR (не отстаёт больше допустимого порога), он автоматически снова попадёт в ISR.
