# РСХБ-Интех (июль 2022 — сентябрь 2024)

## Период 1. Июль — октябрь 2022

**Исходное состояние.** Пришёл в команду цифрового канала ДБО практически сразу после защиты диплома. Сервис универсальных справочников уже существовал, но CRUD был неполным: часть справочников редактировалась через SQL-скрипты вручную, валидация входных данных была разрозненной — где-то на уровне контроллера, где-то вообще отсутствовала.

**Что делал я.**

- Реализовывал CRUD-эндпоинты для оставшихся типов справочников (Spring Boot, Spring Data JPA).
- Ввёл валидацию входящих запросов по JSON Schema вместо разрозненных `@Valid`-аннотаций — схемы справочников часто менялись, а бизнес-аналитики хотели видеть контракт отдельно от кода.
- Столкнулся с проблемой ссылочной целостности: при физическом удалении справочной записи, на которую уже ссылались подписанные документы, при открытии старого документа падал 404/NPE.

**Ошибка и корректировка.** Первая версия эндпоинта `DELETE` делала физическое удаление. На стейджинге всплыл кейс с уже подписанным договором, ссылавшимся на удалённую запись справочника — юридически значимый документ "терял" данные. Заменил на soft-delete + версионирование записей (новая версия при изменении, старые версии остаются доступны по историческому запросу).

**Результат периода.** Закрыл миграцию последних 4 справочников с ручного SQL на API; ссылочная целостность документов перестала ломаться при редактировании справочников.

**Распределение времени:** 20% — онбординг и доступы; 45% — CRUD/валидация; 15% — versioning-фикс; 10% — тесты; 10% — код-ревью/встречи.

## Период 2. Ноябрь 2022 — февраль 2023

**Исходное состояние.** Параллельно стартовал сервис глобальных настроек платформы. Проблема — параметры задавались на нескольких уровнях (банк целиком, филиал, клиент), и не было единой логики, какое значение считать действующим.

**Что делал я.**

- Спроектировал и реализовал логику разрешения итогового значения параметра по иерархии "глобально → филиал → клиент" (cascading override с явным приоритетом более узкого уровня).
- Добавил кэш разрешённых значений — логика вызывалась на каждый запрос форм в UI и была "горячей".

**Ошибка.** Первая версия кэша не инвалидировалась при изменении настройки на промежуточном уровне (филиал) — клиенты какое-то время видели старое значение после того, как филиал менял параметр. Добавил event-based инвалидацию через тот же Kafka-топик, куда писались изменения настроек.

**Результат.** Логика легла в основу последующей пакетной загрузки (период 3); подготовил почву для снижения ручных операций.

**Распределение времени:** 50% — логика разрешения + кэш; 20% — инвалидация/фикс; 15% — тесты; 15% — синхронизация с бизнес-аналитиками.

## Период 3. Март — июнь 2023

**Что делал я.**

- Добавил REST-эндпоинты для пакетной (batch) загрузки индивидуальных настроек клиентов — до этого изменения вносились по одному клиенту вручную через UI, что было основной операционной болью саппорта.
- Параллельно начал дорабатывать сервис счетов на оплату: эндпоинты создания и отслеживания статуса счёта.

**Ключевое решение.** Batch-эндпоинт мог упасть на середине большого файла (тысячи клиентов). Обсуждали с тимлидом — делать ли транзакционным "всё или ничего" или частичным с отчётом об ошибках по строкам. Выбрали второй вариант: частичное применение + построчный отчёт, потому что бизнес не хотел откатывать тысячи успешных изменений из-за одной невалидной строки.

**Результат.** Массовые изменения настроек клиентов перешли с ручных операций на пакетную загрузку.

**Распределение времени:** 40% — batch-загрузка; 30% — счета на оплату (создание/статусы); 15% — тесты; 15% — прочее.

## Период 4. Июль — октябрь 2023

**Исходное состояние.** Сервис счетов на оплату публиковал события об изменении статуса оплаты в Kafka, но при ретраях consumer'а на стороне канала ДБО клиент иногда получал два push-уведомления об одном и том же платеже.

**Что делал я.**

- Интегрировал сервис счетов с Kafka для публикации событий о статусе оплаты (начато в п.3, доведено до продакшена здесь).
- Настроил дедупликацию входящих событий через Redis (ключ — идентификатор счёта + статус + временное окно).

**Production-инцидент.** Уже после релиза, при кратковременном лаге consumer-группы (ребаланс партиций) клиенты массово получили дублирующиеся SMS о списании средств. Пришлось экстренно выкатывать дедупликацию, изначально запланированную на следующий период — задача "нагнала" себя раньше срока.

**Результат.** Дублирование уведомлений устранено.

**Распределение времени:** 35% — Kafka-интеграция; 30% — Redis-дедупликация (внеплановая, из-за инцидента); 20% — постмортем и мониторинг; 15% — тесты.

**Результат.** Среднее время SQL-запроса по заявкам снизилось с 800–900 мс до 200–250 мс.

# Сбер (октябрь 2024 — н.в.)

## Период 8. Октябрь 2024 — январь 2025

**Исходное состояние.** Вошёл в команду аналитики и мониторинга по корпоративному кредитованию. Решение о переходе с ETL-поллинга на event-driven архитектуру было принято командой ещё до моего прихода — я присоединился уже под эту задачу. На тот момент данные на дашборды поступали через периодические ETL-джобы на базе поллинга REST-эндпоинтов бизнес-сервисов, задержка появления метрик доходила до 15 минут.

**Что делал я.**

- Первые недели ушли на онбординг в домен: разбор существующих Kafka-топиков (какие события уже публикуются, в каком формате, с какими ключами партиционирования у producer'ов) и разбор legacy ETL-кода, чтобы понять текущую логику агрегации, которую предстояло воспроизвести в новой системе.
- Только ближе к концу периода подключился к проектированию схемы хранения — совместно с тимлидом и архитектором со стороны платформы данных, не единолично: партиционирование по дате, индексы под типовые аналитические запросы.
- Начал первые прототипы REST API для выдачи данных дашбордам (Spring Boot, Spring Data JPA).

**Ключевое решение.** Обсуждали с тимлидом — переписывать существующий ETL сразу целиком или мигрировать по одной группе метрик за раз, оставив старый поллинг как fallback. Выбрали поэтапную миграцию, чтобы не оставить риск-команды без данных на переходный период.

**Распределение времени:** 45% — онбординг, разбор существующих топиков и legacy ETL; 25% — участие в проектировании схемы хранения и API (совместно с тимлидом/архитектором); 15% — первые прототипы; 15% — синхронизации с продуктовыми/риск-командами.

## Период 9. Февраль — май 2025

**Что делал я.**

- Реализовал слой агрегации на Kafka Streams: normalization/ACL, дедупликация через state store  + Redis, репартиционирование по ключам агрегации (клиент/продукт/регион), windowed aggregation.
- Настроил идемпотентную обработку с дополнительной защитой через Redis для сценариев, где основной механизм дедупликации Kafka Streams был временно неполон (кросс-инстансная защита при ребалансе).

**Как устроена дедупликация (уточнение архитектуры).**

Почему сначала смотрим в Redis, а не RocksDB:

|Фактор|RocksDB (Kafka Streams)|Redis|
|---|---|---|
|**Где данные**|Локальный диск + page cache|Обычно полностью в RAM|
|**Структура**|LSM-tree (много уровней SSTables)|Hash-таблица / Skiplist в памяти|
|**Типичная latency**|10–200+ мкс (иногда единицы мс при cache miss)|10–50 мкс (локальный), 100–300 мкс (по сети в том же ДЦ)|
|**При большом state**|Частые cache miss → чтение с диска|Почти всегда RAM|
|**Конкуренция**|Делит CPU/диск с обработкой стримов|Отдельный процесс|

Основной слой — не Redis, а сам Kafka Streams, и это осознанный выбор в пользу единого source of truth:

- Dedup-состояние (`eventId → seen`) хранится в `KeyValueStore` (timestamped), который физически бэкается **compacted changelog-топиком** в Kafka — встроенный механизм Kafka Streams: каждое изменение локального RocksDB-стора реплицируется в этот топик.
- Топология настроена с `processing.guarantee = exactly_once_v2` (EOS): чтение входного события, запись в state store и запись результата в выходной топик коммитятся атомарно в рамках одной Kafka-транзакции. Это и есть source of truth — при падении между шагами транзакция откатывается целиком, промежуточных "наполовину обработанных" состояний не остаётся.
- При падении инстанса новый инстанс, забирающий партицию, восстанавливает локальный RocksDB именно из changelog-топика — dedup-состояние переживает падения нод.

Redis — это не второй source of truth, а fast-path/защитный фильтр поверх основного механизма, закрывающий конкретное узкое место:

- При ребалансе партиций Kafka Streams новый инстанс должен сначала вычитать весь changelog и восстановить RocksDB локально, прежде чем начать обработку — на большом объёме это не мгновенно, есть окно в несколько секунд/десятков секунд, когда партиция уже переехала, а стор ещё "холодный".
- Если в это окно прилетает дубль (например, из-за retry продюсера), новый инстанс мог его пропустить, не видя ещё полного стора.
- Перед записью в state store каждый `eventId` дополнительно проверялся/выставлялся в Redis с TTL, покрывающим worst-case время восстановления стора + запас — это точечный патч под конкретный failure mode (окно ребаланса), а не постоянно активный слой перед каждым eventId и не альтернативный источник истины.
- При недоступности Redis деградация была mostly-safe: система продолжала полагаться на state store/EOS как на основной механизм, просто без дополнительной защиты именно на время ребаланса.

**Ошибка.** Первая версия дедупликации полагалась только на state store Kafka Streams, без Redis-патча. При ребалансе партиций во время нагрузочного теста несколько задач кратковременно обработали один и тот же event дважды — state store ещё не успел восстановиться на новом инстансе. Добавил описанный выше дополнительный слой проверки через Redis с TTL, покрывающий именно окно ребаланса.

**Результат.** Первая группа метрик (по клиенту) полностью переведена на потоковую обработку параллельно со старым ETL.

**Распределение времени:** 50% — Kafka Streams pipeline; 20% — дедупликация/фикс после инцидента на нагрузочном тесте; 20% — тесты (JUnit, Testcontainers, Mockito); 10% — код-ревью.

## Период 10. Июнь — сентябрь 2025

**Что делал я.**

- Довёл миграцию до всех групп метрик (продукт, регион, композитные измерения продукт+регион), полностью отключил старые ETL-джобы.
- Реализовал retry-механизм и dead-letter queue для событий с битой сериализацией — до этого такие события просто терялись, что било по полноте данных.

**Production-инцидент.** Один из legacy-сервисов, исторически не соблюдавший внутренний контракт событий (не публиковавший `eventId`, с денормализованным форматом полей — то, ради чего и существовал ACL с построением составного `eventId`), выкатил новую версию события с изменённым форматом. Изменение было заранее анонсировано на общей встрече трайба, но я не успел обновить маппинг в ACL под новую версию до релиза — часть событий этого сервиса начала уходить в DLQ как невалидные.

**Мои действия:**

- Обнаружил проблему по росту очереди DLQ.
- Оперативно доработал ACL под новую версию контракта.
- Сообщил SRE-команде о необходимости мониторинга DLQ и предоставил бизнес-контекст (какой порог считать критичным, важность отслеживания возраста сообщения, а не только количества) — саму реализацию алертинга (Grafana/Prometheus) сделала SRE-команда.

**Результат.** Время появления данных на дашбордах снизилось с 15 минут до <2 минут; полнота данных выросла до 99,7% благодаря retry + DLQ.

**Распределение времени:** 35% — доведение миграции по всем dimension; 30% — retry/DLQ; 20% — доработка ACL и координация с SRE после инцидента; 15% — тесты.

## Период 11. Октябрь 2025 — январь 2026

**Что делал я.**

- Занимался снижением нагрузки на исходные сервисы: переход с оставшихся точечных polling-эндпоинтов на event-driven сбор. Речь о редко изменяемых справочниках платформы кредитования — справочник кредитных продуктов и справочник регионов/филиалов, использовавшихся как измерения (dimension) для агрегации. Они исторически подтягивались периодическим REST-поллингом сервисов-владельцев, т.к. изменения там редкие и раньше не было смысла заводить под них event-поток. Когда таких запросов накопилось много (несколько сервисов, дёргаемых по расписанию), это стало создавать заметную фоновую нагрузку — перевёл на подписку на события изменения справочников (publish on change).
- Начал работу над производительностью аналитических запросов: p95 времени ответа REST API дашбордов был около 1,2 с при росте объёма исторических данных.

**Ключевое решение.** Партиционирование PostgreSQL по дате было заложено ещё в период 8, но составных индексов под типовые группировки (продукт+регион+период) не хватало. Обсуждали добавление индексов "под каждый фильтр" по отдельности — отклонили, т.к. это раздувало объём индексов и замедляло запись. Выбрали индексы под 3–4 самых частых паттерна запроса дашбордов.

**Распределение времени:** 40% — event-driven миграция оставшихся источников (справочники продуктов и регионов); 35% — анализ и первые оптимизации запросов; 15% — тесты; 10% — код-ревью.

## Период 12. Февраль — июль 2026 (текущий)

**Что делал я.**

- Вынес общую логику маршрутизации по dimension и типовые агрегаторы (Sum, Count, Avg, Ratio) в переиспользуемый конфигурируемый слой поверх Kafka Streams topology. Базовый контракт событий (`eventType`/`eventId` для дедупликации + ACL для сервисов, ему не следующих) существовал с самого начала проекта — эта работа не про создание контракта заново, а про декларативный слой поверх него: новая метрика теперь описывается конфигом (dimension, тип агрегации, окна), а не отдельным Kafka Streams-пайплайном, написанным вручную с нуля.
- Добавил составные индексы под 3–4 самых частых паттерна фильтрации дашбордов (продукт+регион+период) — довёл p95 REST API дашбордов до 400 мс.
- Провёл нагрузочное тестирование нового декларативного слоя на паре тестовых метрик перед раскаткой на всю продуктовую команду.
- Написал внутреннюю документацию/гайд, как продуктовая команда сама может добавить новую метрику через конфиг без участия разработчика платформы — снизило зависимость от меня как единственной точки входа.
- Закрыл оставшийся технический долг по тестовому покрытию критических путей (JUnit, Testcontainers, Mockito) до стабильного уровня.
- Участвовал в код-ревью 2–3 новых интеграций от других продуктовых команд, начавших подключаться к платформе по готовому декларативному конфигу.

**Результат.** Время вывода новой метрики в дашборды снизилось с ~3–5 дней до 1 дня; p95 времени ответа REST API дашбордов снизился с 1,2 с до 400 мс.

**Распределение времени:** 30% — декларативный слой конфигурации метрик; 20% — perf-оптимизация запросов (индексы); 15% — документация и гайд для продуктовых команд; 15% — тесты; 20% — код-ревью новых интеграций.
