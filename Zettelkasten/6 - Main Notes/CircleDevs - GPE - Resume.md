Высоконагруженная B2B FinTech SaaS-платформа для автоматизации и маршрутизации массовых трансграничных выплат удаленным подрядчикам (до 30 000 транзакций в сутки). Система принимает реестры выплат от enterprise-клиентов, списывает средства с баланса, конвертирует валюты и распределяет деньги на локальные банковские карты и криптокошельки через гибридную сеть платежных шлюзов.

**Обязанности на проекте:**

- Разработка и поддержка микросервисов интеграции (API-адаптеров) с внешними платежными системами и банками.
- Реализация бизнес-логики обработки транзакций, валидации данных, генерации отчетности и интеграции с Telegram Bot/WebApp API.
- Написание интеграционных и модульных тестов, локализация и устранение багов в кодовой базе (Bug Fixing), участие в командных Scrum-процессах.

**Ключевые достижения (STAR / ABT):**

1. Изначально валидация реквизитов внутри загружаемых клиентами CSV-реестров выполнялась последовательно, **и** это приводило к сильным задержкам ответов бэкенда. **Поэтому** я самостоятельно переработал логику валидации чанков в Spring Batch с использованием многопоточности (`TaskExecutor`), что позволило сократить время обработки стандартного пакета из **5 000 строк** до нескольких секунд без перегрузки CPU.
2.  При покрытии кода тестами выяснилось, что использование in-memory базы H2 не воспроизводило реальное поведение транзакций, **но** ручной подъем локального окружения тормозил сборку CI/CD пайплайна. **Поэтому** я полностью переписал тестовый слой интеграционных тестов микросервиса `Ledger`, внедрив библиотеку **Testcontainers**, и лично написал **120 интеграционных сценариев** (включая симуляцию Race Conditions и отказов Kafka), зафиксировав стабильность сборки.
3. Система обменивается конфиденциальными платежными данными с внешними партнерами, **и** любые уязвимости в сетевых запросах могли скомпрометировать ключи клиентов. **Поэтому** я взял на себя задачу по реализации криптографической подписи запросов на основе алгоритма HMAC-SHA256 и настройки валидации временных меток (Timestamp/Nonce), полностью защитив API шлюза от атак повторения (Replay Attacks).
4. Сервис генерации закрывающих документов должен был мгновенно реагировать на успешные выплаты, **но** прямые REST-запросы между сервисами приводили к потере данных при перезагрузках модулей. **Поэтому** я перевел взаимодействие между финансовым ядром и сервисом документов на асинхронную модель, написав кастомные Kafka Producers/Consumers и настроив DLT (Dead Letter Topics) очереди для надежной изоляции сбойных сообщений.
5. На этапе закрытого бета-тестирования возникла проблема двойных выплат из-за скрытого бага в API одного из банков-партнеров, **но** команда не могла локализовать проблему из-за отсутствия сквозных логов. **Поэтому** я провел Root Cause анализ инцидента в Kibana, выявил некорректное поведение банковского шлюза при таймаутах и разработал защитный "cool-down" механизм в рамках нашей политики повторных запросов (Retry Policy), полностью решив проблему дублей.

**Технологический стек проекта:**  
Java 17, Spring Boot 3.x, Spring Data JPA, Spring Batch, Apache Kafka, PostgreSQL, Redis, Resilience4j (Retry/Circuit Breaker), WebSockets, Testcontainers, JUnit 5, Mockito, Logback (ELK/Kibana), Git, Docker.

**О проекте (Global Payout Engine):**  
 B2B FinTech SaaS-платформа для автоматизации и маршрутизации массовых трансграничных выплат удаленным подрядчикам (до 30 000 транзакций в сутки). Система принимает реестры выплат от enterprise-клиентов, списывает средства с баланса, конвертирует валюты и распределяет деньги на локальные банковские карты и криптокошельки через гибридную сеть платежных шлюзов.

**Обязанности на проекте:**

- Проектирование микросервисной архитектуры ядра платформы (Core Ledger) и модулей интеграции с внешними API банками и OTC-провайдерами.
- Реализация отказоустойчивых механизмов обработки платежей, систем идемпотентности, безопасности и распределенных транзакций.
- Руководство подкомандой из 4 бэкенд-разработчиков, декомпозиция архитектурных задач, проведение Code Review и настройка CI/CD пайплайнов (SonarQube Quality Gates).

**Ключевые достижения (STAR / ABT):**

1. **[Числовая метрика]** Платформа должна была обрабатывать тяжелые реестры выплат, **но** классическая пакетная обработка приводила к утечкам памяти (`OutOfMemoryError`) при загрузке файлов. **Поэтому** я спроектировал и внедрил архитектуру потокового парсинга на базе Spring Batch и AWS S3, что позволило системе стабильно и без сбоев обрабатывать реестры объемом **100 000 строк**, удерживая потребление RAM в фиксированных пределах.
2. **[Числовая метрика]** В периоды массовых выплат банковские API сильно задерживали ответы, **и** классическая потоковая модель выедала системные ресурсы, угрожая падением серверов. **Поэтому** я перевел сетевой слой микросервиса `Payout Gateway Integrator` на виртуальные потоки (Java 21 / Project Loom) и оптимизировал пулы соединений, что позволило системе удерживать до **3 000 параллельных HTTP-сессий** на скромных вычислительных мощностях без деградации производительности.
3. Система оперирует миллионными транзакциями, **и** любая гонка данных (Race Condition) при одновременных выплатах могла привести к краже или дублированию средств. **Поэтому** я разработал подсистему Core Ledger на базе гибридного Event Sourcing и уровня изоляции `REPEATABLE READ` в PostgreSQL с оптимистическими блокировками (`@Version`), полностью исключив риски финансового фрода.
4. При падении сети или таймаутах внешних банков возникал риск рассинхронизации данных, **но** стандартные повторные POST-запросы приводили к двойным списаниям у клиентов. **Поэтому** я спроектировал многоуровневый механизм идемпотентности (с распределенным фильтром в Redis и Unique Constraints в БД) и внедрил стратегию асинхронного опроса статусов (Status Inquiry via Resilience4j), гарантировав атомарность транзакций по принципу «Exactly-Once».
5. Бизнес требовал гарантировать доставку платежных событий между микросервисами, **но** падение Java-приложений в момент сетевой отправки приводило к потере сообщений в Kafka. **Поэтому** я интегрировал архитектурный паттерн Transactional Outbox с использованием Debezium (Kafka Connect) для чтения WAL-логов PostgreSQL, обеспечив 100% консистентность данных между финансовым ядром и интеграционными шлюзами.

**Технологический стек проекта:**  
Java 21, Spring Boot 3.3, Spring Data JPA, Spring Cloud, Spring Batch, Spring Security OAuth2, Apache Kafka, Debezium, PostgreSQL, Redis, Resilience4j, Testcontainers, Docker, Kubernetes, AWS S3, GitLab CI/CD, SonarQube.
