## 2. Основные настройки, которые хранит сервис

*Раздел сформирован по предоставленным вами данным — состав категорий подтверждён источниками.*

### 2.1. Системные (глобальные) настройки

| Категория | Состав | Назначение |
|---|---|---|
| **Настройки глобальных параметров** | Общесистемные константы и технические параметры платформы | Базовая техническая конфигурация, не привязанная к конкретному продукту |
| **Настройки интерфейсов** | Конфигурация фронтенда и мобильного приложения | Управление поведением и отображением клиентских приложений без релиза |
| **Настройки безопасности** | Список «белых» IP-адресов | Ограничение доступа к системе по сетевому периметру |
| **Настройки модулей и продуктов** | Параметры РКО, ВЭД, зарплатного проекта, писем, выписок, чата, уведомлений | Поведенческая конфигурация конкретных продуктовых доменов |
| **Настройки визуализации** | Главная страница, витрина сервисов, спецпредложения, рекламные согласия | Управление контентом и персонализацией интерфейса |

### 2.2. Индивидуальные настройки клиентов

Отдельный пункт меню «Загрузка индивидуальных настроек для клиентов» *[подтверждено]* — позволяет переопределять глобальные параметры системы для **конкретных организаций или групп пользователей**. Это единственная в источниках прямо названная операция над клиентскими настройками — судя по формулировке «загрузка», операция пакетная (массовая), а не точечное редактирование одного параметра одному клиенту через форму.

**[допущение]** Раз в источнике явно говорится именно о «загрузке» (а не о «редактировании» через UI-форму), логично предположить, что основной сценарий работы с клиентскими настройками — импорт файла/пакета, а не ручной ввод по одному значению. Раздел 6 ниже детализирует этот эндпоинт.

## 3. Жизненный цикл сущностей

### 3.1. Определение параметра (`SettingDefinition`)

```
ЗАРЕГИСТРИРОВАН → АКТИВЕН → УСТАРЕЛ (deprecated) → УДАЛЁН
```
Параметр регистрируется доменом-владельцем (например, РКО регистрирует `RKO.PAYMENT_LIMIT_DAILY`), после чего становится доступен для установки значения на любом уровне иерархии.

### 3.2. Значение параметра (`SettingValue`) — с учётом иерархии областей

```
ГЛОБАЛЬНОЕ (обязательный уровень, default)
   └─ ФИЛИАЛ (опционально, переопределяет глобальное)
        └─ КЛИЕНТ (опционально, переопределяет филиал и глобальное)
```

Состояния значения:
```
ЧЕРНОВИК → ОПУБЛИКОВАНО → АРХИВНАЯ ВЕРСИЯ (при обновлении, историчность)
```

Значения не перезаписываются — публикация новой версии архивирует предыдущую, что даёт возможность узнать, какое значение действовало для клиента в конкретный момент в прошлом (важно при разборе инцидентов: «почему клиенту в мае было доступно другое поведение системы»).

### 3.3. Индивидуальная настройка клиента как частный случай `SettingValue`

Клиентская настройка технически — это `SettingValue` с `scope = CLIENT`. Отдельного ЖЦ для неё нет, но есть особенность: она может быть создана **только пакетно**, через операцию импорта (раздел 6), в отличие от глобальных настроек, которые публикуются по одной через форму администратора.

## 4. Схема данных

```sql
-- Определение параметра
CREATE TABLE setting_definition (
    id                  UUID PRIMARY KEY,
    key                 VARCHAR(128) UNIQUE NOT NULL,  -- 'RKO.PAYMENT_LIMIT_DAILY', 'SECURITY.IP_WHITELIST_ENABLED'
    category            VARCHAR(32) NOT NULL,           -- GLOBAL_PARAM / INTERFACE / SECURITY / MODULE / VISUALIZATION
    domain              VARCHAR(64),                     -- 'RKO', 'VED', 'SALARY_PROJECT', 'FRONTEND', ...
    value_type          VARCHAR(32) NOT NULL,           -- BOOLEAN / NUMBER / STRING / JSON
    schema_json         JSONB,
    default_value       JSONB NOT NULL,
    is_client_overridable BOOLEAN DEFAULT TRUE,
    is_branch_overridable BOOLEAN DEFAULT TRUE,
    status              VARCHAR(32) NOT NULL,           -- REGISTERED / ACTIVE / DEPRECATED / DELETED
    created_at          TIMESTAMP,
    updated_at          TIMESTAMP
);

-- Значение параметра с учётом области действия
CREATE TABLE setting_value (
    id                  UUID PRIMARY KEY,
    setting_definition_id UUID REFERENCES setting_definition(id),
    scope               VARCHAR(16) NOT NULL,           -- GLOBAL / BRANCH / CLIENT
    scope_id            VARCHAR(64),                     -- NULL для GLOBAL, branch_id или client_id
    value               JSONB NOT NULL,
    status              VARCHAR(32) NOT NULL,           -- DRAFT / PUBLISHED / ARCHIVED
    published_at        TIMESTAMP,
    published_by        VARCHAR(128),
    source              VARCHAR(32),                     -- MANUAL / BATCH_IMPORT
    import_batch_id     UUID,                            -- ссылка на пакет загрузки (для CLIENT-настроек)
    version              INT DEFAULT 1,
    UNIQUE (setting_definition_id, scope, scope_id, version)
);

-- Список белых IP-адресов (отдельная сущность из-за специфики структуры данных)
CREATE TABLE ip_whitelist_entry (
    id                  UUID PRIMARY KEY,
    scope               VARCHAR(16) NOT NULL,           -- GLOBAL / CLIENT
    scope_id            VARCHAR(64),
    ip_address          INET NOT NULL,
    cidr_mask           INT,
    description         VARCHAR(255),
    status              VARCHAR(32) NOT NULL,           -- ACTIVE / REVOKED
    created_at          TIMESTAMP
);

-- Пакет загрузки индивидуальных настроек клиентов
CREATE TABLE settings_import_batch (
    id                  UUID PRIMARY KEY,
    uploaded_by         VARCHAR(128) NOT NULL,
    file_name           VARCHAR(255),
    total_rows          INT,
    success_rows        INT,
    failed_rows         INT,
    status              VARCHAR(32) NOT NULL,           -- PROCESSING / COMPLETED / COMPLETED_WITH_ERRORS / FAILED
    error_report_json   JSONB,
    created_at          TIMESTAMP,
    completed_at        TIMESTAMP
);

-- Аудит изменений
CREATE TABLE setting_audit_log (
    id                  UUID PRIMARY KEY,
    setting_value_id    UUID REFERENCES setting_value(id),
    action              VARCHAR(32),                     -- CREATE / PUBLISH / ARCHIVE / OVERRIDE / IMPORT
    changed_by          VARCHAR(128),
    diff_json           JSONB,
    changed_at          TIMESTAMP
);
```

## 6. Детально: логика разрешения (resolution) итогового значения

### 6.1. Принцип

Разрешение значения — это выбор **самого специфичного** из существующих значений параметра для конкретного контекста запроса (клиент + его филиал), при этом порядок приоритета строго фиксированный:

```
КЛИЕНТ  >  ФИЛИАЛ  >  ГЛОБАЛЬНОЕ
(наивысший приоритет)      (наинизший, всегда существует как fallback)
```

Глобальное значение — обязательный уровень (существует всегда, для любого зарегистрированного параметра). Филиальное и клиентское — опциональны и переопределяют только то, для чего явно созданы.

### 6.2. Алгоритм (псевдокод)

```
function resolve(key, clientId):
    definition = getDefinition(key)
    if definition.status != ACTIVE:
        raise SettingNotActiveError

    branchId = getBranchIdForClient(clientId)   # клиент банка привязан к филиалу оформления договора

    # 1. Пытаемся найти значение на уровне клиента
    if definition.isClientOverridable:
        clientValue = findPublishedValue(key, scope=CLIENT, scopeId=clientId)
        if clientValue exists:
            return { value: clientValue.value, resolvedScope: CLIENT }

    # 2. Пытаемся найти значение на уровне филиала
    if definition.isBranchOverridable and branchId is not null:
        branchValue = findPublishedValue(key, scope=BRANCH, scopeId=branchId)
        if branchValue exists:
            return { value: branchValue.value, resolvedScope: BRANCH }

    # 3. Возвращаем глобальное значение (гарантированно существует)
    globalValue = findPublishedValue(key, scope=GLOBAL, scopeId=null)
    return { value: globalValue.value, resolvedScope: GLOBAL }
```

### 6.3. Пример разрешения по шагам

Дано:
- Глобальное значение `RKO.PAYMENT_LIMIT_DAILY` = 5 000 000 ₽
- Значение на уровне филиала «Краснодарский РФ» = 3 000 000 ₽ (более консервативный лимит для региона)
- Индивидуальное значение для клиента «АО Интро» = 50 000 000 ₽ (крупный корпоративный клиент с индивидуальными условиями)

Запрос `resolve(RKO.PAYMENT_LIMIT_DAILY, clientId=АО_Интро)`:
1. Клиент привязан к филиалу «Краснодарский РФ».
2. Проверяется уровень CLIENT → найдено значение 50 000 000 ₽ → **возвращается оно**, уровень филиала и глобальный уровень не рассматриваются дальше.

Ответ API:
```json
{
  "key": "RKO.PAYMENT_LIMIT_DAILY",
  "resolvedScope": "CLIENT",
  "value": { "amount": 50000000, "currency": "RUB" },
  "resolutionTrace": [
    { "scope": "CLIENT", "found": true, "value": 50000000 },
    { "scope": "BRANCH", "found": true, "value": 3000000, "used": false },
    { "scope": "GLOBAL", "found": true, "value": 5000000, "used": false }
  ]
}
```

**[допущение]** Поле `resolutionTrace` — не подтверждённая источниками деталь, добавлена для наглядности и диагностируемости: администратору часто нужно понять не только итоговое значение, но и почему оно именно такое (иначе support-запрос «почему у клиента другой лимит» решается только через прямой запрос в БД).

### 6.4. Кэширование результата разрешения

Поскольку `resolve` вызывается на каждый запрос пользователя (например, при каждой попытке создать платёж), результат кэшируется на стороне сервиса-потребителя с инвалидацией по Kafka-событию (см. раздел 8.3), а не запрашивается заново при каждом обращении. TTL кэша — **[допущение]**, конкретное значение не описано в источниках; для параметров с высокой критичностью (лимиты, feature flags безопасности) кэш, вероятно, короче или не используется вовсе.

### 6.5. Особый случай: параметр, запрещённый к переопределению

Если `is_client_overridable = false` (например, критичный параметр безопасности, который банк не готов отдавать под индивидуальную настройку), шаг 1 алгоритма пропускается независимо от наличия записи в БД на уровне клиента — попытка её создать через импорт (раздел 7) должна отклоняться на этапе валидации пакета, а не молча игнорироваться при resolution.

## 7. Детально: пакетная загрузка индивидуальных настроек клиентов

### 7.1. Эндпоинт

```
POST /api/v1/admin/settings/clients/import
Content-Type: multipart/form-data

file: settings_batch_2026-07-30.csv
```

### 7.2. Формат входного файла [допущение — конкретный формат не описан в источниках, выбран CSV как типовой для банковских импортов]

```csv
client_id,setting_key,value,valid_from
client-uuid-1234,RKO.PAYMENT_LIMIT_DAILY,50000000,2026-08-01
client-uuid-1234,VED.CURRENCY_CONTROL_THRESHOLD,10000,2026-08-01
client-uuid-5678,FRONTEND.SHOW_LOYALTY_BANNER,false,2026-08-01
```

### 7.3. Обработка запроса — пошагово

1. Файл загружается, создаётся запись `settings_import_batch` со статусом `PROCESSING`, клиенту (администратору) сразу возвращается `batchId` — обработка асинхронная, не блокирующая HTTP-соединение.
2. Построчная валидация:
   - существует ли `setting_key` и активен ли (`ACTIVE`);
   - разрешено ли переопределение на уровне клиента (`is_client_overridable = true`);
   - соответствует ли `value` схеме валидации (`schema_json`) — например, число, а не строка, для параметра типа `NUMBER`;
   - существует ли `client_id` в системе (сверка с доменом «Управление клиентами» — см. раздел 8).
3. Валидные строки публикуются как `SettingValue` со `scope = CLIENT`, `source = BATCH_IMPORT`, `import_batch_id = <id пакета>`.
4. Невалидные строки фиксируются в `error_report_json` с указанием номера строки и причины, не прерывая обработку остальных строк пакета (принцип "частичный успех допустим").
5. После обработки всех строк статус пакета переводится в `COMPLETED` (все строки успешны) либо `COMPLETED_WITH_ERRORS` (часть строк отклонена).

### 7.4. Ответ на инициацию загрузки

```json
{
  "batchId": "batch-uuid-9001",
  "status": "PROCESSING",
  "totalRows": 3,
  "statusUrl": "/api/v1/admin/settings/clients/import/batch-uuid-9001/status"
}
```

### 7.5. Ответ на проверку статуса (после завершения обработки)

```json
{
  "batchId": "batch-uuid-9001",
  "status": "COMPLETED_WITH_ERRORS",
  "totalRows": 3,
  "successRows": 2,
  "failedRows": 1,
  "errors": [
    {
      "row": 3,
      "clientId": "client-uuid-5678",
      "settingKey": "FRONTEND.SHOW_LOYALTY_BANNER",
      "reason": "VALUE_TYPE_MISMATCH: ожидается BOOLEAN, получено 'false' как строка"
    }
  ]
}
```

### 7.6. Идемпотентность

**[допущение]** Повторная загрузка того же файла (например, при случайном повторном клике администратора) не должна создавать дублирующиеся значения — реализуется через уникальность `(setting_definition_id, scope, scope_id, version)` в сочетании с проверкой: если для клиента уже опубликовано значение с тем же `value` и `valid_from`, новая версия не создаётся, пакет помечает строку как `SKIPPED_DUPLICATE`, а не как ошибку.

### 7.7. Уведомление доменов-потребителей об импорте

После завершения пакета в Kafka публикуется одно агрегированное событие (не по одному событию на строку, чтобы не создавать всплеск нагрузки при импорте тысяч строк):

```json
{
  "event": "SETTINGS_BATCH_IMPORTED",
  "batchId": "batch-uuid-9001",
  "affectedClientIds": ["client-uuid-1234", "client-uuid-5678"],
  "affectedKeys": ["RKO.PAYMENT_LIMIT_DAILY", "VED.CURRENCY_CONTROL_THRESHOLD", "FRONTEND.SHOW_LOYALTY_BANNER"],
  "completedAt": "2026-07-30T14:20:00Z"
}
```

Домены-потребители, кэширующие resolved-значения для указанных `affectedClientIds`, инвалидируют локальный кэш точечно, не дожидаясь TTL.

## 8. Разграничение прав пользователей

| Роль | Права |
|---|---|
| **Администратор платформы** | Полный CRUD по определениям и глобальным значениям, откат версий, доступ ко всем категориям настроек |
| **Администратор безопасности** | Только категория «Настройки безопасности» (список белых IP); не имеет доступа к продуктовым параметрам |
| **Продуктовый администратор домена** (например, ВЭД) | CRUD только по параметрам своего домена в категории «Настройки модулей и продуктов» |
| **Оператор по работе с клиентами** | Только операция «Загрузка индивидуальных настроек для клиентов» (POST /import) и просмотр статуса своих пакетов; не может публиковать глобальные значения или регистрировать новые параметры |
| **Сервисный потребитель** (домен платформы, service-to-service) | Только `GET /api/v1/settings/**` (включая `/resolve`), без доступа к `/admin/**` |
| **Аудитор** | Только чтение `setting_audit_log` и истории пакетов импорта |

## 9. Интеграции — с кем и как

### 9.1. Кому сервис предоставляет данные

| Домен-потребитель | Что использует | Зачем |
|---|---|---|
| Auth и доступ | Настройки безопасности (белый список IP), пороги 2FA | Проверка условий входа |
| Документооборот и РКО | Лимиты платежей, настройки подписания | Валидация операций, в т.ч. с учётом индивидуальных лимитов клиента |
| ВЭД (в домене Продукты) | Пороги валютного контроля | Валидация контрактов |
| Продукты и НСИ | Настройки главной страницы, витрины, спецпредложений | Персонализация интерфейса под конкретного клиента |
| Фронтенд / мобильное приложение | Настройки интерфейсов | Feature flags и UI-конфигурация без релиза |
| Коммуникации | Настройки писем, чата, уведомлений | Включение/выключение каналов, шаблоны |

### 9.2. От кого сервис получает данные

| Источник | Что поступает |
|---|---|
| АРМ Администратора (ручной ввод) | Публикация глобальных и филиальных значений |
| Файл через «Загрузку индивидуальных настроек для клиентов» | Пакетное создание клиентских значений (раздел 7) |
| Домен «Управление клиентами» (сверка) | Проверка существования `client_id` при валидации импорта [допущение — вызов через REST к сервису управления клиентами] |

### 9.3. Протоколы

**REST (синхронный)** — основной канал для `resolve` и административных операций. Пример уже приведён в разделах 6–7.

**Kafka (асинхронный)** — для инвалидации кэша и уведомления о пакетном импорте:

```yaml
kafka:
  brokers: ${KAFKA_BROKERS}
  application_id: ${KAFKA_APPLICATION_ID}
  settings_updated_topic: ${KAFKA_SETTINGS_UPDATED_TOPIC}
  settings_batch_imported_topic: ${KAFKA_SETTINGS_BATCH_IMPORTED_TOPIC}
  ip_whitelist_updated_topic: ${KAFKA_IP_WHITELIST_UPDATED_TOPIC}
  security:
    sasl_ssl: ${KAFKA_SASL_SSL}
    ssl:
      trust_store_location: ${KAFKA_TRUSTSTORE_LOCATION}
      trust_store_password: ${KAFKA_TRUSTSTORE_PASSWORD}
    jaas:
      username: ${APP_KAFKA_USER}
      password: ${APP_KAFKA_PASSWORD}
```

Топики:
- `settings.updated` — точечное изменение одного значения (публикация/архивация вручную через АРМ);
- `settings.batch-imported` — агрегированное событие после завершения пакетной загрузки клиентских настроек;
- `ip-whitelist.updated` — отдельный топик для изменений белого списка IP, выделен из-за критичности для ИБ и вероятной подписки со стороны security-компонентов (API Gateway/WAF), а не только доменных сервисов.

**gRPC — не используется** [допущение, по аналогии с общим стеком платформы, где gRPC не упоминается ни в одном компоненте].

## 10. Нерешённые вопросы (требуют уточнения у команды проекта)

1. Формат файла для пакетной загрузки (CSV/Excel/JSON) — источники подтверждают только факт наличия функции «Загрузка», не формат.
2. Обрабатывается ли импорт синхронно (с ожиданием результата в том же HTTP-запросе) или асинхронно с polling статуса — выбран асинхронный вариант как более реалистичный для потенциально больших файлов, но не подтверждён источниками.
3. Существует ли промежуточный уровень «группа клиентов» (упомянутый в формулировке «для конкретных организаций **или групп пользователей**») как самостоятельный scope между филиалом и клиентом, или это описание того же механизма филиальной/сегментной настройки другими словами.
4. Хранится ли список белых IP-адресов физически в этом же сервисе, или это лишь пункт меню, обращающийся к отдельному security-сервису/API Gateway.
