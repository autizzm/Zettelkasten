# Transactions - Kafka


- **Transaction Coordinator** — модуль в брокере Kafka, который управляет транзакциями и отслеживает их состояние.

- **Transaction Log** — внутренний топик, куда записывается состояние транзакций (например: “начата”, “готова к коммиту”, “завершена”).

### Запись

![[Pasted image 20260201110847.png]]

- Когда продюсер начинает новую транзакцию, он регистрирует свой `transactional.id` у Transaction Coordinator. 
  После этого он начинает отправлять сообщения обычным образом, но в рамках транзакции. Когда приходит время — либо `commitTransaction()`, либо `abortTransaction()`. 
  При коммите Kafka пишет **“маркер”** транзакции в каждую участвующую партицию и фиксирует, что сообщения этой транзакции видимы.

- Потребитель, настроенный в режиме `isolation.level=read_committed`, будет видеть только те записи, которые относятся к **завершённым (committed) транзакциям**, и игнорировать те, что от **незавершённых** или **aborted**.


---

**~={red}?!=~ Transaction Coordinator** в Apache Kafka — это модуль (компонент), который работает **внутри обычного брокера**. Это не отдельный процесс и не специальный тип брокера.

---
### Что он делает

Он отвечает за управление транзакциями продюсеров (atomic writes across multiple partitions + exactly-once semantics):

- Выдаёт и управляет Producer ID (PID) и epoch’ами.
- Отслеживает состояние транзакций (Ongoing → PrepareCommit/PrepareAbort → CompleteCommit/CompleteAbort).
- Координирует двухфазный коммит (отправляет transaction markers на партиции, участвующие в транзакции).
- Хранит метаданные транзакций в специальном внутреннем топике `__transaction_state`.
- Обрабатывает таймауты и восстановление после сбоев.

Каждый брокер при старте создаёт свой экземпляр `TransactionCoordinator`. Этот экземпляр отвечает только за те `transactional.id`, которые «принадлежат» партициям `__transaction_state`, лидером которых является данный брокер.



### Как выбирается Transaction Coordinator

Выбор происходит точно так же, как у Group Coordinator:

1. У каждого транзакционного продюсера есть `transactional.id`.
2. Kafka вычисляет партицию внутреннего топика:
   ```
   partition = Math.abs(transactionalId.hashCode()) % numPartitions(__transaction_state)
   ```
   (по умолчанию у `__transaction_state` 50 партиций).
3. **Лидер этой партиции** — это и есть Transaction Coordinator для данного `transactional.id`.

Продюсер находит координатора через `FindCoordinator`-запрос (отправляет любому брокеру, тот возвращает адрес нужного).

### Высокая доступность
Если брокер-лидер падает, Kafka (через обычный механизм leader election) выбирает нового лидера для соответствующих партиций `__transaction_state`. Новый лидер становится Transaction Coordinator’ом, читает лог и восстанавливает состояние транзакций в памяти.

### Краткий итог
| Вопрос | Ответ |
|--------|--------|
| Это обычный брокер? | Да, это модуль, работающий внутри обычного Kafka-брокера |
| Как выбирается? | По хэшу `transactional.id` → партиция `__transaction_state` → её текущий лидер |
| Сколько их в кластере? | Столько, сколько брокеров, у которых есть лидерство по партициям `__transaction_state` (обычно почти все) |

Это дизайн, очень похожий на Group Coordinator + `__consumer_offsets`.


---
### Чтение

Только два уровня изоляции:

- **read_uncommited** — читать все подряд.

- **read_committed** — читать только закоммиченные сообщения.
