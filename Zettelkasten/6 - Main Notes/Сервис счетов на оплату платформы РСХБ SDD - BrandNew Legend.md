# Приложение: дедупликация входящих событий через Redis — зачем и как

> Контекст: в примере резюме упоминалась фраза «настроил дедупликацию входящих событий через Redis». Ниже — разбор, зачем это нужно и почему это не то же самое, что стандартный inbox-паттерн.

## Как работает классический inbox-паттерн

При получении события consumer в **той же транзакции**, где обрабатывает бизнес-логику, записывает `message_id` в таблицу `inbox` с уникальным ограничением (`UNIQUE(message_id)`). Kafka гарантирует at-least-once (дубликаты — норма при ребалансировке партиций или ретраях producer'а), поэтому повторная вставка в `inbox` упадёт на уникальном ограничении — событие уже обработано, обработку можно безопасно пропустить.

**Плюс:** атомарность — бизнес-запись и отметка об обработке коммитятся вместе, что даёт настоящую консистентность exactly-once на уровне бизнес-эффекта.

**Минус:** каждая проверка — запись/чтение в реляционной БД внутри транзакции, что добавляет нагрузку на PostgreSQL и увеличивает латентность обработки каждого события, особенно при высоком потоке (статусы платежей, чарджи, рефанды — типично высокочастотный поток).

## Зачем тогда Redis

Redis — это **первый, быстрый фильтр** перед тем, как событие вообще дойдёт до бизнес-логики и БД:

```
SET dedup:{message_id} 1 NX EX 300
```

`NX` — записать, только если ключа ещё нет; `EX 300` — TTL 5 минут. Если команда вернула `false` (ключ уже существовал) — событие это дубликат, полученный повторно в короткий промежуток времени (типичная причина — ребалансировка Kafka consumer group или retry на стороне producer'а), и его можно отбросить **до** обращения к БД, экономя время и нагрузку на постоянное хранилище.

**Почему это не заменяет inbox полностью:** между `SET NX` в Redis и фактическим коммитом в PostgreSQL нет транзакционной связи. Если процесс упадёт после установки ключа в Redis, но до записи в БД — событие будет потеряно навсегда (при повторной доставке дедупликация его отбросит, решив, что оно уже обработано, хотя фактически бизнес-эффект не наступил). Это классический trade-off "consistency vs latency".

## Правильная комбинация (то, что вероятнее всего стоит за формулировкой резюме)

Грамотное решение — не либо/либо, а слоёное:

1. **Redis** — быстрый, "оптимистичный" фильтр явных повторов в узком временном окне (TTL 1–5 минут), чтобы не грузить БД одинаковыми событиями при штатных ретраях Kafka.
2. **Идемпотентная запись в БД** как источник истины — не через отдельную inbox-таблицу с `message_id`, а через **natural key** самой бизнес-сущности (например, `UPSERT` по `(invoice_id, event_id)` с `ON CONFLICT DO NOTHING`). Тогда даже если Redis пропустит дубликат по ошибке (TTL истёк, был рестарт Redis без персистентности), повторная обработка не создаст дублирующийся бизнес-эффект.

Redis здесь — оптимизация производительности (не тратить ресурсы БД на заведомо повторные события), а не единственная гарантия корректности; гарантию даёт идемпотентность самой записи в PostgreSQL. Junior+ разработчик вполне мог реализовать именно этот, "быстрый" слой, не проектируя всю двухуровневую схему целиком целенаправленно — что реалистично для такого грейда.

| Параметр | Значение |
|---|---|

## 2. Жизненный цикл сущностей

### 2.1. Счёт на оплату (`Invoice`)

```
ЧЕРНОВИК → ВЫСТАВЛЕН → ОТПРАВЛЕН ПОЛУЧАТЕЛЮ → ОПЛАЧЕН
                                            ↘ ЧАСТИЧНО ОПЛАЧЕН
                                            ↘ ПРОСРОЧЕН
                                            ↘ ОТМЕНЁН (только из ЧЕРНОВИК/ВЫСТАВЛЕН)
```

- **Черновик** — клиент формирует счёт (позиции, суммы, реквизиты плательщика), можно редактировать свободно.
- **Выставлен** — счёт зафиксирован, присвоен номер, дальнейшее редактирование позиций запрещено (только отмена и создание нового счёта).
- **Отправлен получателю** — счёт передан плательщику (по email/ссылке/через витрину сервисов), ожидание оплаты.
- **Оплачен / Частично оплачен / Просрочен** — статусы, наступающие по факту поступления денежных средств или истечения срока оплаты.
- **Отменён** — счёт аннулирован клиентом до наступления оплаты.

Переход в «Оплачен»/«Частично оплачен» — не решение самого сервиса, а результат обработки события о зачислении средств, пришедшего асинхронно (см. раздел 6).

### 2.2. Позиция счёта (`InvoiceLineItem`)

Не имеет собственного ЖЦ — существует только в контексте счёта в статусе «Черновик»; после перехода счёта в «Выставлен» позиции становятся неизменяемым снапшотом.

### 2.3. Событие оплаты (`PaymentEvent`)

```
ПОЛУЧЕНО → ОБРАБОТАНО → ПРИМЕНЕНО К СЧЕТУ
                       ↘ ОТКЛОНЕНО (дубликат/несоответствие суммы)
```

## 3. Схема данных

```sql
CREATE TABLE invoice (
    id                  UUID PRIMARY KEY,
    invoice_number      VARCHAR(32) UNIQUE NOT NULL,
    client_id           UUID NOT NULL,               -- владелец счёта (кто выставляет)
    payer_name          VARCHAR(255) NOT NULL,       -- контрагент-плательщик
    payer_inn           VARCHAR(12),
    total_amount        NUMERIC(18,2) NOT NULL,
    paid_amount         NUMERIC(18,2) DEFAULT 0,
    currency            VARCHAR(3) DEFAULT 'RUB',
    status              VARCHAR(32) NOT NULL,        -- DRAFT / ISSUED / SENT / PAID / PARTIALLY_PAID / OVERDUE / CANCELLED
    due_date            DATE,
    issued_at           TIMESTAMP,
    created_at          TIMESTAMP,
    updated_at          TIMESTAMP
);

CREATE TABLE invoice_line_item (
    id                  UUID PRIMARY KEY,
    invoice_id          UUID REFERENCES invoice(id),
    description         VARCHAR(500) NOT NULL,
    quantity            NUMERIC(12,3) DEFAULT 1,
    unit_price          NUMERIC(18,2) NOT NULL,
    amount              NUMERIC(18,2) NOT NULL
);

CREATE TABLE payment_event (
    id                  UUID PRIMARY KEY,
    invoice_id          UUID REFERENCES invoice(id),
    event_id            VARCHAR(128) NOT NULL,        -- natural key из внешнего события (АБС)
    amount              NUMERIC(18,2) NOT NULL,
    received_at         TIMESTAMP,
    status              VARCHAR(32) NOT NULL,          -- RECEIVED / APPLIED / REJECTED
    reject_reason       VARCHAR(255),
    UNIQUE (invoice_id, event_id)                       -- идемпотентность на уровне БД
);

CREATE TABLE invoice_status_history (
    id                  UUID PRIMARY KEY,
    invoice_id          UUID REFERENCES invoice(id),
    old_status          VARCHAR(32),
    new_status          VARCHAR(32),
    changed_at          TIMESTAMP,
    changed_by          VARCHAR(128)                    -- 'SYSTEM' для автоматических переходов
);
```

Обратите внимание на `UNIQUE (invoice_id, event_id)` в `payment_event` — это пример **идемпотентной записи в БД**, о которой шла речь в приложении про дедупликацию: даже если Redis-фильтр пропустит повторное событие, вставка дубликата в эту таблицу просто не пройдёт (или будет обработана через `ON CONFLICT DO NOTHING`), и повторного зачисления суммы к счёту не произойдёт.

## 4. Use cases и соответствующие эндпоинты

| Use case | Метод/Эндпоинт | Кто вызывает |
|---|---|---|
| Создать черновик счёта | `POST /api/v1/invoices` | Клиент (через фронтенд) |
| Редактировать позиции черновика | `PUT /api/v1/invoices/{id}/line-items` | Клиент |
| Выставить счёт (зафиксировать) | `POST /api/v1/invoices/{id}/issue` | Клиент |
| Отправить счёт получателю (email/ссылка) | `POST /api/v1/invoices/{id}/send` | Клиент |
| Получить список счетов клиента с фильтрами по статусу | `GET /api/v1/invoices?clientId={id}&status=OVERDUE` | Клиент, фронтенд |
| Получить детали счёта | `GET /api/v1/invoices/{id}` | Клиент |
| Отменить счёт | `POST /api/v1/invoices/{id}/cancel` | Клиент |
| Публичная ссылка для просмотра счёта плательщиком (без авторизации в банке) | `GET /api/v1/public/invoices/{token}` | Внешний плательщик (не клиент банка) |
| Применить событие об оплате к счёту (внутренний, вызывается consumer'ом Kafka, не напрямую извне) | *(внутренний обработчик, не публичный REST)* | Kafka consumer сервиса |
| Ручная сверка/применение платежа администратором (edge-case, когда автосопоставление не сработало) | `POST /api/v1/admin/invoices/{id}/apply-payment` | Оператор банка |
| Просмотр истории статусов счёта | `GET /api/v1/invoices/{id}/history` | Клиент, аудитор |

## 5. Разграничение прав пользователей

| Роль | Права |
|---|---|
| **Клиент / уполномоченное лицо клиента** | CRUD собственных счетов (только своих, `client_id` = текущая организация), отправка, отмена |
| **Представитель клиента без права первой подписи** | Может создавать черновики, не может выставлять (`issue`) — [допущение по аналогии с механикой визирования из руководства администратора] |
| **Плательщик (внешнее лицо, не клиент банка)** | Только просмотр по публичной ссылке-токену, без авторизации в системе |
| **Оператор банка** | Ручное применение платежа к счёту при сбое автосопоставления, просмотр всех счетов |
| **Администратор платформы** | Настройка правил автосопоставления платежей, доступ к списку просроченных счетов для отчётности |
| **Сервисный потребитель** (другие домены) | Только `GET /api/v1/invoices/**` для чтения статуса (например, домен коммуникаций — для рассылки напоминаний о просрочке) |

## 6. Интеграции — с кем и как

### 6.1. Кому сервис предоставляет данные

| Домен-потребитель | Что получает | Зачем |
|---|---|---|
| Коммуникации | Статус счёта (просрочен/оплачен) | Отправка уведомлений и напоминаний клиенту |
| Продукты и НСИ (витрина) | Сводка по счетам клиента | Отображение виджета «Счета на оплату» на главной странице |
| Глобальные настройки | Читает `INVOICE.OVERDUE_GRACE_PERIOD_DAYS` и подобные параметры | Настройка периода до перевода в статус «Просрочен» без изменения кода |

### 6.2. От кого сервис получает данные

| Источник | Что поступает | Протокол |
|---|---|---|
| **АБС** (банковское ядро) | События о зачислении средств на счёт клиента (потенциальная оплата счёта) | Kafka, асинхронно |
| Справочники (домен НСИ) | Справочник валют (для мультивалютных счетов) | REST, синхронно при создании счёта |
| Домен управления клиентами | Проверка принадлежности `client_id` | REST, синхронно при создании счёта |

### 6.3. Протоколы

**REST** — весь клиентский CRUD-функционал (раздел 4), синхронный, так как пользователь ждёт немедленного ответа при создании/редактировании счёта.

**Kafka** — для получения событий об оплате из АБС и публикации собственных событий об изменении статуса счёта:

```yaml
kafka:
  brokers: ${KAFKA_BROKERS}
  application_id: ${KAFKA_APPLICATION_ID}
  payment_received_topic: ${KAFKA_PAYMENT_RECEIVED_TOPIC}   # consumer, из АБС
  invoice_status_changed_topic: ${KAFKA_INVOICE_STATUS_CHANGED_TOPIC}  # producer
  security:
    sasl_ssl: ${KAFKA_SASL_SSL}
    ssl:
      trust_store_location: ${KAFKA_TRUSTSTORE_LOCATION}
      trust_store_password: ${KAFKA_TRUSTSTORE_PASSWORD}
    jaas:
      username: ${APP_KAFKA_USER}
      password: ${APP_KAFKA_PASSWORD}
```

Пример входящего события об оплате (из `payment.received`, публикуемого АБС):
```json
{
  "eventId": "abs-evt-778211",
  "accountNumber": "40702810900000012345",
  "amount": 150000.00,
  "currency": "RUB",
  "payerInn": "7701234567",
  "purpose": "Оплата по счёту №INV-2026-000451",
  "receivedAt": "2026-07-30T11:05:00Z"
}
```

Пример исходящего события об изменении статуса счёта (`invoice.status.changed`):
```json
{
  "event": "INVOICE_STATUS_CHANGED",
  "invoiceId": "invoice-uuid-4551",
  "oldStatus": "SENT",
  "newStatus": "PAID",
  "changedAt": "2026-07-30T11:05:03Z"
}
```

### 6.4. Дедупликация входящих событий об оплате — применительно к этому сервису

Именно здесь и нужна логика, обсуждённая в приложении выше:

1. **Redis-фильтр** — на входе Kafka consumer'а: `SET dedup:payment:{eventId} 1 NX EX 600`. Если ключ уже есть — событие отбрасывается сразу, не доходя до бизнес-логики сопоставления суммы со счётом. Это критично, поскольку при ребалансировке партиций Kafka (например, при деплое новой версии сервиса) одно и то же событие о зачислении может прийти повторно в течение нескольких минут.
2. **Идемпотентная запись в `payment_event`** — истинная гарантия корректности: `UNIQUE(invoice_id, event_id)` не позволит дважды зачислить одну и ту же оплату к счёту, даже если Redis-фильтр по какой-то причине не сработал (истёк TTL, был перезапуск Redis).
3. **Почему не только "чистый" inbox без Redis:** при высоком потоке событий (в проекте банковского масштаба — потенциально тысячи зачислений в час) постоянная запись/чтение в PostgreSQL на каждую попытку обработки, включая заведомые повторы, создаёт лишнюю нагрузку на основную транзакционную БД; Redis выносит эту "грязную работу" на более дешёвое и быстрое хранилище, оставляя PostgreSQL для финальной, уже отфильтрованной записи.

**gRPC** — не используется, аналогично остальным сервисам платформы [допущение по общему стеку].

## 7. Нерешённые вопросы

1. Каким образом происходит автоматическое сопоставление входящего платежа с конкретным счётом — по номеру счёта в назначении платежа (как в примере выше), по сумме и ИНН плательщика, или комбинированно; при частичном совпадении сервис должен уметь и не должен ошибочно закрывать не тот счёт.
2. Что происходит при переплате или платеже без указания номера счёта — есть ли отдельный статус/очередь "неопознанных платежей" для ручной сверки оператором.
3. Поддерживает ли сервис мультивалютные счета в реальности, или это теоретическая возможность схемы, не подтверждённая источниками.
