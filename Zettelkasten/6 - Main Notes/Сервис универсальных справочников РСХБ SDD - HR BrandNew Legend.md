# Service Definition Document



## Сервис универсальных справочников (Reference Data Service)
### Платформа НЦК ЮЛ «Свой Бизнес»

---

## 1. Общие сведения

| Параметр | Значение |
|---|---|
| Название сервиса | `reference-data-service` (условное имя, по аналогии с `task-service`, `system-jurnal-service`) |
| Домен | Нормативно-справочная информация (НСИ) |
| Назначение | Централизованное хранение и предоставление справочных (мастер-)данных для всех продуктовых доменов платформы |
| Тип сервиса | Бэковый микросервис, платформенный (сквозной) — обслуживает Auth, РКО, ВЭД, Продукты, Admin |
| Технологии | Java 17, Spring Boot, PostgreSQL ≥12, Liquibase, Apache Kafka ≥3.2.0 [подтверждено общим стеком платформы] |
| Среда развёртывания | Docker-контейнер на AppFarm/Kubernetes [подтверждено] |

## 2. Жизненный цикл сущностей

Сервис оперирует тремя уровнями сущностей: **тип справочника**, **версия справочника**, **запись справочника**.

### 2.1. Справочники, упомянутые в источниках

Из руководства администратора: банки РФ, банки мира, банки-корреспонденты, валюты, каналы, страны, регионы, коды ОКВЭД, курсы валют ЦБ, коды валютных операций, зоны ответственности ССП, уровни доступа по счетам, условия отображения счетов, типы аутентификации, типы документов, типы документов, удостоверяющих личность.

### 2.2. ЖЦ типа справочника (`ReferenceType`)

```
СОЗДАН → АКТИВЕН → УСТАРЕЛ (deprecated) → АРХИВИРОВАН
```

- **Создан** — тип справочника зарегистрирован, но ещё не наполнен записями.
- **Активен** — доступен для чтения потребителями и редактирования администратором НСИ.
- **Устарел** — новые записи не принимаются, старые доступны только для чтения (например, при замене справочника кодов ОКВЭД новой редакцией).
- **Архивирован** — недоступен через основной API, данные сохраняются для аудита/исторических запросов.

Удаление типа справочника **запрещено физически** — только перевод в архив, так как на записи могут ссылаться исторические документы в других доменах (платежи, договоры).

### 2.3. ЖЦ записи справочника (`ReferenceItem`)

```
ЧЕРНОВИК → АКТИВНА → НЕАКТИВНА (soft delete) 
```
Для версионируемых справочников (курсы валют, тарифы, зоны ответственности) дополнительно:
```
АКТИВНА (текущий период) → ИСТОРИЧЕСКАЯ (сохраняется с указанием периода действия)
```

- Записи **никогда не удаляются физически** (hard delete) — только помечаются неактивными, поскольку они могут быть частью снапшота уже подписанного документа (например, банк-корреспондент, указанный в исполненном платеже 2024 года, должен оставаться доступным для просмотра исторической выписки).
- Для курсов валют ЦБ действует ежедневное версионирование: новая запись на дату не заменяет предыдущую, а добавляется с `valid_from = дата`.

**[допущение]** Механизм версионирования не описан в источниках; выбран как типовой паттерн для справочников, критичных к историчности (курсы, тарифы, коды классификаторов).

## 3. Схема данных

Общая (полиморфная) модель, позволяющая не создавать отдельную таблицу под каждый из 15+ справочников:

> [!warning]
> Хранение курса валют - не входит  в зону ответственности данного сервиса


```sql
-- Тип справочника (метаданные)
CREATE TABLE reference_type (
    id              UUID PRIMARY KEY,
    code            VARCHAR(64) UNIQUE NOT NULL,   -- 'BANK_RF', 'CURRENCY', 'OKVED', ...
    name            VARCHAR(255) NOT NULL,
    is_versioned    BOOLEAN DEFAULT FALSE,          -- true для курсов валют, тарифов
    owner_domain    VARCHAR(64),                    -- домен-владелец данных (для внешних источников)
    schema_json     JSONB,                          -- JSON Schema для валидации attributes
    status          VARCHAR(32) NOT NULL,           -- CREATED / ACTIVE / DEPRECATED / ARCHIVED
    created_at      TIMESTAMP,
    updated_at      TIMESTAMP
);

-- Запись справочника
CREATE TABLE reference_item (
    id              UUID PRIMARY KEY,
    reference_type_id UUID REFERENCES reference_type(id),
    code            VARCHAR(64) NOT NULL,           -- 'RUB', '044525225' (БИК), '62.01' (ОКВЭД)
    attributes      JSONB NOT NULL,                 -- {"name": "Российский рубль", "num_code": "643"}
    valid_from      DATE,
    valid_to        DATE,                           -- NULL = бессрочно
    status          VARCHAR(32) NOT NULL,           -- DRAFT / ACTIVE / INACTIVE
    version         INT DEFAULT 1,
    created_at      TIMESTAMP,
    updated_at      TIMESTAMP,
    UNIQUE (reference_type_id, code, valid_from)
);

-- Аудит изменений
CREATE TABLE reference_audit_log (
    id              UUID PRIMARY KEY,
    reference_item_id UUID REFERENCES reference_item(id),
    action          VARCHAR(32),                    -- CREATE / UPDATE / DEACTIVATE
    changed_by      VARCHAR(128),                    -- логин сотрудника банка
    diff_json       JSONB,
    changed_at      TIMESTAMP
);
```

**Пример записи** (справочник валют):
```json
{
  "reference_type": "CURRENCY",
  "code": "USD",
  "attributes": {
    "name_ru": "Доллар США",
    "num_code": "840",
    "min_unit": 100
  },
  "status": "ACTIVE"
}
```

**Пример версионированной записи** (курс валют ЦБ на дату):
```json
{
  "reference_type": "CB_CURRENCY_RATE",
  "code": "USD",
  "attributes": { "rate": 92.4567, "nominal": 1 },
  "valid_from": "2026-07-29",
  "valid_to": "2026-07-29"
}
```

Каждый справочник версионируется миграциями через Liquibase [подтверждено — паттерн описан в руководстве по установке для `task-service`: `liquibase/changelog.yaml`, `default_schema`].

## 4. Use cases и соответствующие эндпоинты

| Use case | Метод/Эндпоинт | Кто вызывает |
|---|---|---|
| Получить список активных значений справочника | `GET /api/v1/references/{typeCode}` | Все домены (валидация форм) |
| Получить одну запись по коду | `GET /api/v1/references/{typeCode}/{code}` | Домен документооборота (проверка БИК банка) |
| Получить курс валюты ЦБ на дату | `GET /api/v1/references/currency-rates?currency=USD&date=2026-07-29` | Домен ВЭД, домен продуктов (конверсия) |
| Получить справочник, актуальный на дату (историческая версия) | `GET /api/v1/references/{typeCode}?asOfDate=2025-01-01` | Аудит, выписки за прошлый период |
| Создать/обновить запись справочника | `PUT /api/v1/admin/references/{typeCode}/{code}` | АРМ Администратора |
| Массовая загрузка справочника (импорт) | `POST /api/v1/admin/references/{typeCode}/import` | АРМ Администратора (например, полная замена справочника ОКВЭД новой редакцией) |
| Деактивировать запись | `DELETE /api/v1/admin/references/{typeCode}/{code}` *(soft delete)* | АРМ Администратора |
| Просмотр истории изменений записи | `GET /api/v1/admin/references/{typeCode}/{code}/audit` | Аудитор |
| Управление жизненным циклом типа справочника (deprecate/archive) | `PATCH /api/v1/admin/reference-types/{typeCode}/status` | НСИ-администратор |
| Проверка целостности (валидация кода перед использованием) | `GET /api/v1/references/{typeCode}/{code}/exists` | Домен документооборота (перед сохранением документа) |

**[допущение]** Форматы путей и разбиение на `/references` (публичное, read-only) и `/admin/references` (защищённое, write) выбраны по типовой практике REST API для reference data сервисов; в источниках прямых URL нет.

## 5. Разграничение прав пользователей

Опирается на упомянутую в руководстве администратора **ролевую модель** (`Управление → Ролевая модель`) и разделение ролей banка/клиента.

| Роль | Права |
|---|---|
| **НСИ-администратор** (сотрудник банка) | Полный CRUD по всем справочникам, управление ЖЦ типов справочников, массовый импорт |
| **НСИ-оператор** (сотрудник банка) | CRUD по справочникам, не относящимся к регуляторным классификаторам (например, может править «Справочник каналов», но не «Коды ОКВЭД», которые синхронизируются из внешнего источника — только чтение) |
| **Сервисный потребитель** (service-to-service, любой домен платформы) | Только `GET` на `/api/v1/references/**`, без доступа к `/admin/**` |
| **Аудитор** | Только чтение `audit_log`, без права изменения данных |
| **Клиент / представитель клиента** | Косвенный, только через UI других доменов (например, видит справочник валют в форме платежа) — прямого доступа к API справочников не имеет |

Авторизация — через домен Auth/доступ (JWT/сессионный токен с ролью в claims), сервис справочников сам не хранит учётные данные пользователей [допущение, согласуется с общей архитектурой: домен Auth — единая точка входа].

## 6. Интеграции — с кем и как

### 6.1. Кому сервис предоставляет данные (потребители)

| Домен-потребитель       | Какие справочники использует                                                              | Зачем                                     |
| ----------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------- |
| Документооборот и РКО   | Банки РФ, банки-корреспонденты, типы документов, типы документов, удостоверяющих личность | Валидация реквизитов при создании платежа |
| ВЭД (в домене Продукты) | Страны, коды валютных операций, курсы валют ЦБ, коды ОКВЭД                                | Валютный контроль, оформление контрактов  |
| Продукты и НСИ          | Каналы, регионы, уровни доступа по счетам, условия отображения счетов                     | Настройка витрины и видимости продуктов   |
| АРМ Администратора      | Все справочники                                                                           | Ведение и редактирование НСИ              |

### 6.2. От кого сервис получает данные (внешние источники)

| Внешний источник                              | Справочник           | Периодичность                                                                        |
| --------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------ |
| ФНС / внешний классификатор                   | Коды ОКВЭД           | По мере выхода новой редакции классификатора (нерегулярно) - **~={orange}вручную=~** |
| Внутренний банковский справочник контрагентов | Банки-корреспонденты | По расписанию/событийно                                                              |

**[допущение]** Прямого упоминания синхронизации с ЦБ РФ или ФНС в источниках нет — это стандартная практика для банковских систем и логически необходимо, так как справочник курсов валют не может наполняться вручную ежедневно.

### 6.3. Протоколы интеграции

**REST (синхронный, основной канал для потребителей).**
Используется, когда домен должен получить справочные данные *в момент* обработки запроса пользователя (например, валидация БИК при вводе платёжного поручения) — задержка на устаревшие данные недопустима, нужен ответ здесь и сейчас.

```
GET /api/v1/references/BANK_RF/044525225 HTTP/1.1
Host: reference-data-service.internal
Authorization: Bearer <service-jwt>

200 OK
{
  "code": "044525225",
  "attributes": { "name": "ПАО Сбербанк", "swift": "SABRRUMM" },
  "status": "ACTIVE"
}
```

**Kafka (асинхронный, для оповещения об изменениях).**
Используется не для получения данных "по запросу", а для **инвалидации локальных кэшей** в доменах-потребителях: справочники читаются часто и меняются редко, поэтому каждый домен, вероятно, кэширует их у себя, а сервис справочников рассылает событие об изменении, чтобы кэш обновился без постоянного опроса.

Топики [по аналогии с нотацией `application.yml` из руководства по установке]:

```yaml
kafka:
  brokers: ${KAFKA_BROKERS}
  application_id: ${KAFKA_APPLICATION_ID}
  reference_updated_topic: ${KAFKA_REFERENCE_UPDATED_TOPIC}
  currency_rate_updated_topic: ${KAFKA_CURRENCY_RATE_UPDATED_TOPIC}
  security:
    sasl_ssl: ${KAFKA_SASL_SSL}
    ssl:
      trust_store_location: ${KAFKA_TRUSTSTORE_LOCATION}
      trust_store_password: ${KAFKA_TRUSTSTORE_PASSWORD}
    jaas:
      username: ${APP_KAFKA_USER}
      password: ${APP_KAFKA_PASSWORD}
```

Пример сообщения в топике `reference.updated`:
```json
{
  "event": "REFERENCE_ITEM_UPDATED",
  "referenceType": "BANK_RF",
  "code": "044525225",
  "timestamp": "2026-07-29T10:15:00Z",
  "version": 3
}
```

Пример сообщения в топике `currency-rate.updated`:
```json
{
  "event": "CURRENCY_RATE_UPDATED",
  "currency": "USD",
  "rate": 92.4567,
  "validFrom": "2026-07-29"
}
```

## 7. Нерешённые вопросы (требуют уточнения у команды проекта)

1. Как физически синхронизируются курсы ЦБ и коды ОКВЭД — через отдельный интеграционный adapter-сервис или это часть самого reference-data-service.
2. Используется ли Redis/иной кэш перед PostgreSQL для горячих справочников (валюты, банки) — в источниках кэширующий слой не упомянут вовсе.
3. Согласуется ли схема `reference_item.attributes (JSONB)` с реальной моделью, или каждый справочник в проекте физически хранится в отдельной таблице (что тоже соответствует наблюдаемому в проекте паттерну "один сервис — одна схема", но менее гибко для 15+ разнородных справочников).
