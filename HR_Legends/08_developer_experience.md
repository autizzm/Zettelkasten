# 08. Developer Experience

См. также [[05_team_structure]], [[06_tech_stack]].

## Окружения

| Окружение | Назначение |
|---|---|
| **local** | docker-compose: PostgreSQL, Kafka (single broker), mock Camunda, WireMock для внешнего источника данных об арестах |
| **dev** | Общее окружение потока, авто-деплой на каждый мердж в `develop` |
| **test/QA** | Регресс, включая сценарии обрыва Kafka-консюмера/сети к внешнему источнику; проверка поведения на маскированных синтетических ПДн |
| **stage (preprod)** | Обязательный шаг перед релизом изменений в саге и в `legal-holds-integration-service` |
| **prod** | С канареечным сегментом трафика |

Прод-данные не копируются в непрод-окружения без маскирования — обязательный pipeline маскирования/синтетических данных, особенно для QA юридических сценариев (см. [[04_data_flows#Комплаенс и защита персональных данных]]).

## Git-workflow

- Trunk-based, короткоживущие feature-ветки (`feature/ROP-XXXX-...`), 1–3 дня.
- `release/x.y` — отсекается перед регрессом, только фиксы.
- `hotfix/x.y.z` — от прод-тега, упрощённый процесс (approve тимлида + сокращённый прогон).
- Conventional Commits, squash-merge в `develop`.
- Отдельная метка `contract-change` для PR, меняющих Kafka-схему события — обязательное ревью всех потребителей топика, даже если они в других командах.

## Время релизов

- Домен «Проблемные активы» — раз в 2–3 недели, не жёстко к спринту: фактическую дату чаще определяет комплаенс-гейт (см. [[05_team_structure#Комплаенс-гейт домен Проблемные активы]]), а не готовность кода.
- Хотфиксы — вне расписания, по факту инцидента.

## Процесс: от задачи до прода

1. **Постановка.** Тикет в Jira от аналитика. Для нетривиальных задач — «3 амиго» на груминге/рефайнменте, до Planning Poker.
2. **Комплаенс-гейт** (для домена «Проблемные активы», если задача касается задолженности/арестов/взысканий) — привлечение юр./комплаенс на этапе постановки, для высокорисковых сценариев — DPIA до начала разработки.
3. **Оценка и декомпозиция** — Planning Poker.
4. **Разработка** в feature-ветке. Для изменений в саге/компенсациях — design-note (happy path + failure path) в Confluence, ревью тимлида до старта реализации. Для изменений в Kafka-контракте — PR с меткой `contract-change`.
5. **Тесты.** Unit → компонентные (embedded Kafka + Testcontainers Postgres) → интеграционные (полный цикл через тестовый Camunda-движок).
6. **Code review.** Обязательный approve; для `debt-case-service` и BPMN-процессов — approve тимлида.
7. **Деплой в test/QA**, регресс QA, ручная проверка сценариев саги (включая намеренный обрыв сети к внешнему источнику на stage).
8. **Релиз в прод** через canary (5% → 25% → 100%) с автооткатом по метрикам ошибок — обязателен для `debt-case-service` и `restructuring-workflow-service`.
9. **Пост-релизный мониторинг**: consumer lag, доля `evt.newTermsApplied(success=false)`, глубина DLQ-топика (только структурно повреждённые сообщения), возраст `FAILED`-записей в inbox.

## Тестовая пирамида

| Уровень | Что покрывает | Инструменты |
|---|---|---|
| Unit | Бизнес-логика внутри сервиса | JUnit |
| Компонентные | Взаимодействие сервиса с Kafka/БД в изоляции | Embedded Kafka, Testcontainers (Postgres) |
| Интеграционные | Полный цикл saga через реальный движок | Тестовый Camunda-движок |
| Contract-тесты | Совместимость схемы события с JSON Schema | CI, `contracts/kafka/*.schema.json` |

## Типовые зоны ответственности в потоке «Проблемные активы»

Ниже — иллюстрация того, какого рода задачи типично встречаются в потоке (для ориентира при онбординге и планировании нагрузки), а не хроника одного человека: перечисленный объём распределён между 3–4 backend-инженерами потока и обязательно проходит ревью тимлида для изменений, затрагивающих сагу или `debt-case-service` (см. [[05_team_structure#Два потока внутри одной команды]]).

- **Доменная модель и inbox/outbox:** проектирование `DebtCase`, `RestructuringProposal`, `LegalHold`, `CollectionEvent`; inbox-consumer для saga cmd-топиков; outbox-relay для доменных событий.
- **Saga orchestration:** compensation Service Task'и, `RestructuringWorkflowLock`, разделение operator/client и saga путей изменения статуса.
- **Устойчивость внешних интеграций:** consumer для `legal-holds-integration-service` — трёхзначная семантика ответа, circuit breaker + bulkhead.
- **Миграция:** batch reconciliation job (`MigrationBatch` → `ReconciliationRecord`), классификация расхождений.
- **Контракты событий:** проектирование и согласование JSON Schema для Kafka-топиков, настройка contract-тестов в CI.
- **Эксплуатационная рутина:** гонки на границах часовых поясов/DST в расчётах (например, `overdueDays`), пагинация и фильтрация в списковых эндпоинтах, валидация входящих webhook-payload'ов, Flyway-миграции при добавлении полей, runbook для дежурного (разбор `FAILED`-записей inbox, admin-replay).
- **Ревью.** Ревью PR коллег внутри потока, обязательное для изменений Kafka-контрактов — по чек-листу совместимости.

## Инцидент: несовместимая схема события

Показательный пример того, почему contract-тесты и `schemaVersion` (см. [[03_services#Формат сообщений и совместимость схем]]) стали обязательной практикой, а не опцией.

**Что произошло.** До введения contract-тестов поле `overdueAmount` в `rop.debt.case.status-changed` было изменено с плоского числа на вложенный объект `{amount, currency}` без согласования с владельцем `collection-notification-service` — изменение расценили как достаточно тривиальное, чтобы не затевать отдельное ревью контракта.

**Импакт.** `collection-notification-service` десериализовал событие через строгий Jackson-маппинг без толерантности к смене типа поля — каждое новое сообщение в топике вызывало исключение десериализации. Consumer не коммитил offset при ошибке и застрял на первом же сообщении нового формата. За ~6 часов, пока не сработал алерт на монотонно растущий consumer lag, ~140 клиентов не получили уведомление о смене статуса дела (в частности, о снятии ареста).

**Как чинили.** Откат формата события до плоского числа (hotfix в `debt-case-service`), повторная публикация непроведённых событий из outbox (недоставленные записи уже там хранились — упростило replay), ручная инициализация уведомлений по 140 накопленным кейсам силами оператора.

**Новое правило** (уже отражено как стандарт в [[03_services#Формат сообщений и совместимость схем]]): любое изменение существующего поля в Kafka-событии — не только добавление — обязано пройти PR с меткой `contract-change` и явным ревью владельцев всех consumer'ов топика; переименование/смена типа поля запрещены в принципе, вместо этого заводится новый `eventType`/суффикс. Обязательное поле `schemaVersion` в конверте — чтобы подобные несовместимости были видны на уровне конверта, а не только через exception в проде.

## Наблюдаемость на дежурстве

- Consumer lag — растущий и не сокращающийся лаг сигнализирует о застрявшем (не просто отстающем) консьюмере.
- Возраст `FAILED`-записей в inbox — алертинг в ops/комплаенс, восстановление через явную admin-операцию (`FAILED → RECEIVED`), не через реконсьюм из Kafka.
- Глубина инфраструктурного DLQ-топика — только структурно повреждённые сообщения, не бизнес-ошибки.
