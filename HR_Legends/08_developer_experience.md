# 08. Developer Experience

См. также [[05_team_structure]], [[06_tech_stack]].

## Окружения

| Окружение | Назначение |
|---|---|
| **local** | docker-compose: PostgreSQL, Kafka (single broker), mock Camunda, WireMock для внешнего источника данных об арестах |
| **dev** | Общее окружение потока, авто-деплой на каждый мердж в `develop` |
| **test/QA** | Регресс, включая сценарии обрыва Kafka-консюмера/сети к внешнему источнику; проверка поведения на маскированных синтетических ПДн |
| **stage (preprod)** | Обязательный шаг перед релизом изменений в саге и в `legal-holds-integration-service` |
| **prod** | С канареечным сегментом трафика |

Прод-данные не копируются в непрод-окружения без маскирования — обязательный pipeline маскирования/синтетических данных, особенно для QA юридических сценариев (см. [[04_data_flows#Комплаенс и защита персональных данных]]).

## Git-workflow

- Trunk-based, короткоживущие feature-ветки (`feature/ROP-XXXX-...`), 1–3 дня.
- `release/x.y` — отсекается перед регрессом, только фиксы.
- `hotfix/x.y.z` — от прод-тега, упрощённый процесс (approve тимлида + сокращённый прогон).
- Conventional Commits, squash-merge в `develop`.
- Отдельная метка `contract-change` для PR, меняющих Kafka-схему события — обязательное ревью всех потребителей топика, даже если они в других командах.

## Время релизов

- Домен «Проблемные активы» — раз в 2–3 недели, не жёстко к спринту: фактическую дату чаще определяет комплаенс-гейт (см. [[05_team_structure#Комплаенс-гейт домен Проблемные активы]]), а не готовность кода.
- Хотфиксы — вне расписания, по факту инцидента.

## Процесс: от задачи до прода

1. **Постановка.** Тикет в Jira от аналитика. Для нетривиальных задач — «3 амиго» на груминге/рефайнменте, до Planning Poker.
2. **Комплаенс-гейт** (для домена «Проблемные активы», если задача касается задолженности/арестов/взысканий) — привлечение юр./комплаенс на этапе постановки, для высокорисковых сценариев — DPIA до начала разработки.
3. **Оценка и декомпозиция** — Planning Poker.
4. **Разработка** в feature-ветке. Для изменений в саге/компенсациях — design-note (happy path + failure path) в Confluence, ревью тимлида до старта реализации. Для изменений в Kafka-контракте — PR с меткой `contract-change`.
5. **Тесты.** Unit → компонентные (embedded Kafka + Testcontainers Postgres) → интеграционные (полный цикл через тестовый Camunda-движок).
6. **Code review.** Обязательный approve; для `debt-case-service` и BPMN-процессов — approve тимлида.
7. **Деплой в test/QA**, регресс QA, ручная проверка сценариев саги (включая намеренный обрыв сети к внешнему источнику на stage).
8. **Релиз в прод** через canary (5% → 25% → 100%) с автооткатом по метрикам ошибок — обязателен для `debt-case-service` и `restructuring-workflow-service`.
9. **Пост-релизный мониторинг**: consumer lag, доля `evt.newTermsApplied(success=false)`, глубина DLQ-топика (только структурно повреждённые сообщения), возраст `FAILED`-записей в inbox.

## Тестовая пирамида

| Уровень | Что покрывает | Инструменты |
|---|---|---|
| Unit | Бизнес-логика внутри сервиса | JUnit |
| Компонентные | Взаимодействие сервиса с Kafka/БД в изоляции | Embedded Kafka, Testcontainers (Postgres) |
| Интеграционные | Полный цикл saga через реальный движок | Тестовый Camunda-движок |
| Contract-тесты | Совместимость схемы события с JSON Schema | CI, `contracts/kafka/*.schema.json` |

## Типовые зоны ответственности в потоке «Проблемные активы»

Ниже — иллюстрация того, какого рода задачи типично встречаются в потоке (для ориентира при онбординге и планировании нагрузки), а не хроника одного человека: перечисленный объём распределён между 3–4 backend-инженерами потока и обязательно проходит ревью тимлида для изменений, затрагивающих сагу или `debt-case-service` (см. [[05_team_structure#Два потока внутри одной команды]]).

- **Доменная модель и inbox/outbox:** проектирование `DebtCase`, `RestructuringProposal`, `LegalHold`, `CollectionEvent`; inbox-consumer для saga cmd-топиков; outbox-relay для доменных событий.
- **Saga orchestration:** compensation Service Task'и, `RestructuringWorkflowLock`, разделение operator/client и saga путей изменения статуса.
- **Устойчивость внешних интеграций:** consumer для `legal-holds-integration-service` — трёхзначная семантика ответа, circuit breaker + bulkhead.
- **Миграция:** batch reconciliation job (`MigrationBatch` → `ReconciliationRecord`), классификация расхождений.
- **Контракты событий:** проектирование и согласование JSON Schema для Kafka-топиков, настройка contract-тестов в CI.
- **Эксплуатационная рутина:** гонки на границах часовых поясов/DST в расчётах (например, `overdueDays`), пагинация и фильтрация в списковых эндпоинтах, валидация входящих webhook-payload'ов, Flyway-миграции при добавлении полей, runbook для дежурного (разбор `FAILED`-записей inbox, admin-replay).
- **Ревью.** Ревью PR коллег внутри потока, обязательное для изменений Kafka-контрактов — по чек-листу совместимости.

## Инцидент: несовместимая схема события

Показательный пример того, почему contract-тесты и `schemaVersion` (см. [[03_services#Формат сообщений и совместимость схем]]) стали обязательной практикой, а не опцией.

**Что произошло.** До введения contract-тестов поле `overdueAmount` в `rop.debt.case.status-changed` было изменено с плоского числа на вложенный объект `{amount, currency}` без согласования с владельцем `collection-notification-service` — изменение расценили как достаточно тривиальное, чтобы не затевать отдельное ревью контракта.

**Импакт.** `collection-notification-service` десериализовал событие через строгий Jackson-маппинг без толерантности к смене типа поля — каждое новое сообщение в топике вызывало исключение десериализации. Consumer не коммитил offset при ошибке и застрял на первом же сообщении нового формата. За ~6 часов, пока не сработал алерт на монотонно растущий consumer lag, ~140 клиентов не получили уведомление о смене статуса дела (в частности, о снятии ареста).

**Как чинили.** Откат формата события до плоского числа (hotfix в `debt-case-service`), повторная публикация непроведённых событий из outbox (недоставленные записи уже там хранились — упростило replay), ручная инициализация уведомлений по 140 накопленным кейсам силами оператора.

**Новое правило** (уже отражено как стандарт в [[03_services#Формат сообщений и совместимость схем]]): любое изменение существующего поля в Kafka-событии — не только добавление — обязано пройти PR с меткой `contract-change` и явным ревью владельцев всех consumer'ов топика; переименование/смена типа поля запрещены в принципе, вместо этого заводится новый `eventType`/суффикс. Обязательное поле `schemaVersion` в конверте — чтобы подобные несовместимости были видны на уровне конверта, а не только через exception в проде.


## 6. Поведенческие кейсы

### 6.1. Конфликт

**Ситуация.** При проектировании саги реструктуризации возник спор с командой, отвечающей за `collection-notification-service`, по поводу семантики события `evt.termsProposed`. Я исходил из того, что `restructuring-workflow-service` должен продолжать процесс только после подтверждения, что уведомление реально доставлено клиенту, — иначе SLA-таймер эскалации мог начать тикать раньше, чем клиент физически узнал о предложении. Команда `collection-notification-service` настаивала на оптимистичной модели: событие публикуется сразу после постановки уведомления в очередь их внутренней notification-платформы, без ожидания подтверждения фактической доставки — по их мнению, ожидание усложнило бы их сервис избыточной статусной моделью ради одного потребителя.

**Действия.** Я подготовил конкретные сценарии, где расхождение статусов приводило к проблеме: эскалация могла сработать до того, как клиент вообще узнал о предложении. Показал это на встрече с владельцем `collection-notification-service`. Договориться сразу не удалось: они предлагали просто увеличить SLA-таймер с запасом, я — добавить отдельный статус подтверждения доставки в контракт. Поскольку решение влияло на контракт события с несколькими потребителями, вопрос вынесли на архитектурный обзор с тимлидами обеих команд — с представлением обоих вариантов и их компромиссов, а не попыткой продавить решение в переписке.

**Итог.** Приняли промежуточное решение: `collection-notification-service` использует уже существующее в контракте техническое событие `rop.notifications.sent`/`.failed` как статус постановки в очередь, а мой SLA-таймер стартует не от `termsProposed`, а от `notifications.sent` с дополнительным запасом, рассчитанным по статистике фактической доставки push-уведомлений. Полноценное отслеживание доставки на уровне устройства признали избыточным для этой задачи.

---

### 6.2. Провал

**Что произошло.** До того как contract-тесты и обязательное поле `schemaVersion` (сейчас описанные в §4.4 архитектурного документа как стандарт) стали обязательной практикой, я внёс изменение в формат события `rop.debt.case.status-changed`: поле `overdueAmount` было плоским числом, а по запросу аналитиков для поддержки будущей мультивалютности я поменял его на вложенный объект `{amount, currency}` — без согласования с владельцем `collection-notification-service`, посчитав изменение достаточно тривиальным, чтобы не затевать отдельное ревью контракта.

**Импакт.** `collection-notification-service` десериализовал событие через строгий Jackson- маппинг (без толерантности к смене типа поля) — каждое новое сообщение в топике стало приводить к исключению десериализации. Consumer не коммитил offset при ошибке и после нескольких ретраев отправлял сообщения в DLQ Примерно за **6 часов**, пока проблему не заметили, накопилось около **140 сообщений** и сработал алерт. 

**Как чинили.** Проблему заметили по алерту на рост DLQ: `collection-notification-service` (лаг рос монотонно и не сокращался — верный признак застрявшего, а не просто отстающего консьюмера). Эскалировал тимлиду сразу. Вместе приняли решение: откатить формат события до плоского числа (`hotfix` в `debt-case-service`, повторная публикация непроведённых событий из outbox — по счастью, outbox уже хранил недоставленные записи, что упростило replay), и вручную инициировать уведомления по 140 накопленным кейсам силами оператора, пока consumer не разгрёб лаг самостоятельно.

**Вывод и новое правило.** После разбора инцидента (blameless post-mortem) в команде закрепили правило, которое сейчас формализовано в архитектурном документе: **любое изменение существующего поля в Kafka-событии (не только добавление) обязано пройти PR с меткой `contract-change` и явным ревью владельцев всех consumer'ов топика; переименование или смена типа поля запрещены в принципе — вместо этого заводится новый `eventType`/суффикс, старый формат живёт до миграции всех потребителей.** Так же в событие добавили обязательное поле `schemaVersion`, чтобы подобные несовместимости были видны уже на уровне конверта, а не только через exception в проде.

### 6.3. Интересная задача

**Контекст.** Camunda коррелирует входящие `evt`-сообщения в конкретный экземпляр процесса по ключу `caseId` — это предполагает, что на один `caseId` в любой момент времени существует не более одного активного экземпляра процесса реструктуризации. На старте у нас не было ничего, что гарантировало бы этот инвариант — `POST /restructuring/{caseId}/start` просто запускал новый экземпляр процесса без проверки, есть ли уже активный.

**Как обнаружили проблему.** На стадии QA на stage нашли сценарий: оператор в UI дважды нажал «Начать реструктуризацию» из-за задержки ответа сети — фронтенд не блокировал повторный клик, и ушло два вызова `start`. Оба успешно создали экземпляр процесса Camunda для одного и того же `caseId`. Дальше стало интересно: когда пришло `evt.termsProposed`, Camunda скоррелировал сообщение в **один** из двух экземпляров — но какой именно, было недетерминировано с точки зрения нашей бизнес-логики (зависело от внутренней реализации message correlation в движке, не документированной как публичный контракт). Второй экземпляр остался «сиротой», продолжая ждать событие, которое к нему уже не придёт, — то есть тихо завис бы до истечения SLA-таймера и ушёл в компенсацию по делу, которое на самом деле успешно продвигалось в первом экземпляре.

**Рассмотренные варианты и trade-off'ы:**

1. **Заблокировать повторный клик только на фронтенде.** Не решение, а костыль — тот же race возможен при легитимном ретрае на нестабильной сети без участия пользователя (тот же UUID запроса, но два TCP-соединения) или при повторном вызове из автоматизированного скрипта восстановления после сбоя. Отклонено как решение не на своём уровне.
2. **Полагаться на `aggregateVersion`/оптимистичную блокировку `DebtCase`.** Оптимистичная блокировка защищает от одновременной _записи_ в саму сущность, но не мешает запустить два _процесса_, которые ещё не дошли до записи — проблема на уровне корреляции сообщений, а не на уровне записи в БД. Не решает исходную проблему.
3. **Распределённый лок через Redis/ZooKeeper.** Технически работает, но добавляет инфраструктурную зависимость ради инварианта, который по сути — обычное ограничение уникальности в реляционной модели. Отклонено как избыточное усложнение для команды, у которой и так уже есть PostgreSQL под рукой.
4. **Собственная таблица-лок с атомарной проверкой (выбранный вариант).** `RestructuringWorkflowLock(caseId PK, activeProcessInstanceId, lockedAt)` в `debt-case-service` (том же сервисе, что уже владеет консистентностью `DebtCase`, а не в `restructuring-workflow-service`, чтобы лок был рядом с данными, которые он защищает). `POST /start` перед стартом процесса атомарно выполняет `INSERT ... ON CONFLICT (caseId) DO NOTHING` — если конфликт, второй вызов отклоняется с понятной бизнес-ошибкой «процесс уже запущен», а не тихо создаёт второй экземпляр. Лок снимается при переходе процесса в терминальное состояние (успех, компенсация, ручная эскалация).

**Дополнительный нюанс.** Пришлось отдельно решать, что происходит, если процесс падает аварийно (краш инстанса Camunda) без штатного перехода в терминальное состояние — лок в этом случае остаётся висеть навсегда. Добавили фоновую проверку: если `lockedAt` старше порога (с запасом относительно максимальной ожидаемой длительности легитимного процесса) и по `activeProcessInstanceId` в самой Camunda нет активного экземпляра — лок считается orphaned и снимается автоматически, с записью в `rop.audit.event`.

**Результат.** Повторный/параллельный запуск процесса реструктуризации на одном `caseId` стал физически невозможен на уровне API, а не полагался на дисциплину фронтенда или клиента API. Проблема неоднозначной корреляции в Camunda перестала быть теоретическим риском.


## Наблюдаемость на дежурстве

- Consumer lag — растущий и не сокращающийся лаг сигнализирует о застрявшем (не просто отстающем) консьюмере.
- Возраст `FAILED`-записей в inbox — алертинг в ops/комплаенс, восстановление через явную admin-операцию (`FAILED → RECEIVED`), не через реконсьюм из Kafka.
- Глубина инфраструктурного DLQ-топика — только структурно повреждённые сообщения, не бизнес-ошибки.
