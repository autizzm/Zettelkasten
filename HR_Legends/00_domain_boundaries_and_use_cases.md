
**Роль системы в целом**

ROP (Retail Operations Platform) — это **внутренняя пост-продажная операционная платформа** банка. Она автоматизирует процессы **после** точки продажи розничных продуктов:

- Выдача клиентских документов (справки, выписки, квитанции).
- Сопровождение проблемной задолженности (реструктуризация, учёт арестов/взысканий, миграция с legacy-системы взыскания).

Это **не** фронтальная система (оформление кредита/карты), **не** система принятия кредитных решений и **не** система первичного риск-скоринга. Она работает с уже выданными продуктами и уже возникшими проблемами.

Два домена работают относительно независимо внутри одной команды:
- «Документы» — уже в пилотной эксплуатации.
- «Проблемные активы» — в проде, идёт поэтапная миграция со strangler-fig.

### Ответ на вопрос про ФССП

Вы правы: **через публичный API ФССП (`api-ip.fssp.gov.ru`) нельзя закрыть дело о долге банка**. API даёт только **чтение** сведений из банка данных исполнительных производств:

- поиск ИП по ФИО + дата рождения + регион (ФЛ);
- поиск по наименованию/адресу (ЮЛ);
- поиск по номеру ИП;
- групповые (асинхронные) запросы.

Никаких операций «закрыть», «отозвать», «внести изменения» в исполнительное производство через этот API нет. Это и не нужно.

**Зачем интеграция в ROP:**

Банк — **взыскатель** (или потенциальный). Когда у клиента появляется исполнительное производство **от других кредиторов / госорганов** (арест счетов, имущества, взыскание), это критически влияет на работу с его долгом перед банком:

- Может быть наложен арест на счета → платежи по реструктуризации не проходят или проходят частично.
- Меняется приоритет взыскания.
- Нужно уведомлять клиента и операторов.
- Нужно учитывать это в статусе `DebtCase` и в процессе реструктуризации.

`legal-holds-integration-service` делает именно это:
- Асинхронно (poll + batch) запрашивает ФССП.
- Через внутренний ACL переводит текстовую классификацию предмета исполнения в доменные события (`rop.legal.hold.detected` / `released` / `partially-paid`).
- Публикует также generic-событие `rop.legal.fssp-check.completed` для потребителей **вне** ROP (Risk Monitoring, онбординг/KYC).
- Работает fail-open: недоступность ФССП не блокирует клиента (результат помечается stale).
- Изолирован circuit breaker + bulkhead + rate-limiter.

Дополнительно система получает подтверждения платежей по арестам от **платёжного шлюза банка** (`rop.payments.legal-hold.payment-confirmed`) и может отмечать частичное погашение.

То есть интеграция — **мониторинг внешних юридических обременений клиента**, а не управление собственными исполнительными производствами банка.

### Связь с системой оценки риска дефолта

Документация прямо говорит, что **Risk Monitoring System** — внешняя система. Она:

- Обнаруживает риск-сигналы о просрочке.
- Публикует `rop.risk.overdue-signal.detected` → `debt-case-service` открывает `DebtCase`.

ROP **не** оценивает вероятность дефолта и **не** принимает решение «открывать дело или нет». Она **реагирует** на уже сформированный сигнал. Это правильное разделение ответственности:

- Risk-система = обнаружение + скоринг/модели.
- ROP = операционное сопровождение уже открытого проблемного дела (реструктуризация, уведомления, учёт арестов, миграция legacy).

Тесная интеграция есть, но она **событийная и односторонняя** (Risk → ROP). Обратной связи в виде «ROP влияет на модели риска» в текущей документации нет (и это нормально для пост-продажного слоя).

## 1. Формализованные границы системы

### Что система **должна** делать

| Область | Обязанности |
|---------|-------------|
| Документы | Приём заявок на документы, валидация, асинхронная генерация (HTML/CSS → PDF), архивирование, доставка по каналам, отмена, повторная доставка. |
| Проблемные активы | Открытие/ведение `DebtCase` по сигналу риска или вручную оператором; запуск и оркестрация процесса реструктуризации (Camunda saga); учёт платежей; мониторинг и учёт внешних арестов/взысканий (ФССП); уведомления клиенту; поэтапная миграция legacy-дел (extract → validate → reconcile → cutover). |
| Общее | Аудит всех юридически значимых действий; идемпотентность; соблюдение 152-ФЗ (ПДн, data residency, crypto-shredding для права на удаление). |

### Что система **не должна** делать

- Хранить мастер-данные клиента (это CRM).
- Обнаруживать/скорить риск просрочки (Risk Monitoring System).
- Доставлять push/SMS/email напрямую (Notification Platform).
- Проводить платежи (платёжный шлюз).
- Вести сами исполнительные производства в ФССП или подавать документы в ФССП.
- Оформлять/выдавать кредитные продукты, карты и т.п. (фронтальные системы).
- Быть source of truth по статусу клиента в целом.

### На что система должна **реагировать**

- Сигналы просрочки от Risk Monitoring (`rop.risk.overdue-signal.detected`).
- Изменения профиля клиента от CRM (`rop.crm.customer.updated` → инвалидация кэша).
- Новые/изменённые исполнительные производства ФССП (через poll).
- Подтверждения платежей по арестам от платёжного шлюза.
- Действия операторов контакт-центра и клиентов (заявки на документы, ответы на предложения реструктуризации, ручное изменение статуса дела).
- Команды саги реструктуризации и компенсирующие команды.

### Пользователи системы

| Роль | Канал | Что делает |
|------|-------|------------|
| Оператор контакт-центра | HTTPS (через API Gateway) | Работа с делами, запуск/мониторинг реструктуризации, просмотр документов, ручное создание дела, смена статуса (operator path). |
| Клиент банка | Mobile / Web-кабинет | Запрос документов, просмотр статуса, принятие/отклонение условий реструктуризации. |
| Аналитик миграции / комплаенс | Специализированные UI / API | Просмотр reconciliation-отчётов, cutover, аудит-логи. |
| Внешние системы | Kafka / REST | Risk, CRM, Notification Platform, платёжный шлюз, ФССП (poll), legacy (миграция). |

## 2. Данные: входы / выходы и внешние интеграции

### Внутри банковского контура

| Система | Направление | Способ | Данные |
|---------|-------------|--------|--------|
| **CRM** | В ← ROP | REST (профиль) + Events (`rop.crm.customer.updated`) | Мастер-данные клиента (чтение + инвалидация кэша). |
| **Risk Monitoring System** | В → ROP | Kafka (`rop.risk.overdue-signal.detected`) | Сигнал о просрочке (clientId + контекст). ROP также публикует generic `rop.legal.fssp-check.completed` обратно. |
| **Notification Platform** | ROP → | Kafka / API | Команды на отправку уведомлений; статус доставки (`rop.notifications.sent/failed`). |
| **Платёжный шлюз** | В → ROP | Events (`rop.payments.legal-hold.payment-confirmed`) | Подтверждение оплаты по аресту. |
| **Legacy Collection System** | ROP ↔ | Kafka + API | Extract батчей, сверка, миграция дел, cutover. |
| **Auth (OAuth2/OIDC)** | — | REST (auth-gateway) | Аутентификация/авторизация (не событийная модель). |

### За пределами банковского контура

| Система | Направление | Способ | Данные |
|---------|-------------|--------|--------|
| **ФССП** (`api-ip.fssp.gov.ru`) | ROP → (poll) | REST (асинхронный batch/group) | Поиск ИП по ФИО/дате/региону или номеру. Только чтение. Результат проецируется в доменные события hold.*. |
| **Объектное хранилище (S3)** | Внутри ROP | SDK | PDF-документы, чекпоинты `StatementNode`. |
| **Клиент / Оператор** | ↔ | HTTPS (REST через API Gateway) | Заявки, статусы, ответы на предложения, скачивание документов. |

**Ключевые потоки данных наружу:**
- Уведомления клиенту (через Notification Platform).
- Аудит-события (`rop.audit.event`).
- Generic-результат скрининга ФССП (для Risk/KYC).

**Ключевые потоки внутрь:**
- Сигнал риска → открытие дела.
- Профиль клиента.
- Платежи по арестам.
- Ответы клиента на предложения реструктуризации (через notification-сервис).

Способы: преимущественно **Kafka** (доменные события и команды саги) + **REST** (синхронные запросы состояния, захват лока, внешний poll ФССП). gRPC в документации не используется.

## 3. Use cases системы и декомпозиция на сервисы

### Домен «Документы»

**UC-D1. Клиент/оператор запрашивает документ**
1. `document-request-service`: принимает `POST /document-requests` (с Idempotency-Key) → публикует `rop.docs.request.created`.
2. `document-generation-engine`: Assembly (дерево `StatementNode`) → Render (PDF) → `rop.docs.document.generated` (или `.generation-failed`).
3. `document-archive-service`: сохраняет в S3 → `rop.docs.document.archived`.
4. `document-delivery-service`: доставляет по каналу → `rop.docs.document.delivered` / `.delivery-failed`.
5. `document-request-service`: обновляет статус заявки.

**UC-D2. Отмена заявки** — `document-request-service` публикует `rop.docs.request.cancelled` → generation-engine останавливает работу.

**UC-D3. Активация новой версии шаблона** — `document-template-registry` → `rop.docs.template.activated` → generation-engine инвалидирует кэш.

### Домен «Проблемные активы»

**UC-P1. Открытие проблемного дела**
- Триггер: `rop.risk.overdue-signal.detected` **или** ручной `POST /debt-cases` оператором.
- `debt-case-service` создаёт `DebtCase` (status=NEW) → `rop.debt.case.opened` (+ aggregateVersion).

**UC-P2. Запуск реструктуризации (happy path)**
1. Оператор/система: `POST /restructuring/{caseId}/start`.
2. `restructuring-workflow-service` синхронно захватывает `RestructuringWorkflowLock` в `debt-case-service`.
3. Camunda: `cmd.proposeTerms` → `collection-notification-service` → уведомление клиенту → `evt.termsProposed`.
4. Клиент отвечает → `evt.clientResponded`.
5. При принятии: `cmd.applyNewTerms` → `debt-case-service` (inbox) → `evt.newTermsApplied`.
6. `cmd.closeOldCase` → статус RESTRUCTURED → CLOSED.
7. Лок снимается.

**UC-P3. Failure / компенсация**
- При `success=false` или SLA-таймере: Error Boundary → компенсации `compensateApplyNewTerms` + `compensateProposeTerms` (ретраятся до успеха, без SLA).
- Статус возвращается в IN_PROGRESS, proposal → COMPENSATED, лок снимается, пишется аудит.

**UC-P4. Мониторинг арестов ФССП**
1. `legal-holds-integration-service` (scheduler) делает poll/batch к API ФССП.
2. ACL → доменные события `hold.detected` / `released` / `partially-paid`.
3. `debt-case-service` и `collection-notification-service` реагируют (обновление статуса / уведомление).
4. Параллельно: generic `fssp-check.completed` уходит наружу.

**UC-P5. Платёж по аресту**
- Платёжный шлюз → `rop.payments.legal-hold.payment-confirmed` → `legal-holds-integration-service` → возможное `hold.partially-paid`.

**UC-P6. Миграция legacy (strangler fig)**
1. `legacy-collection-migration-service`: extract batch → validate → daily reconciliation.
2. При стабильном отсутствии mismatch → cutover класса дел.
3. Слушает `case.opened` / `case.status-changed` с буферизацией по `aggregateVersion`.
4. Публикует `case.migrated` → `debt-case-service`.

**UC-P7. Уведомления и эскалация**
- `collection-notification-service` обрабатывает команды propose/compensate и события hold/status-changed.
- SLA-таймер эскалации стартует от фактического `rop.notifications.sent` (не от постановки в очередь).

**UC-P8. Аудит и комплаенс**
- Все значимые действия → `rop.audit.event` → `audit-logging-service`.
- Доступ к документам и делам — RBAC/ABAC + проверка владельца.

### Краткие выводы и возможные улучшения документации

1. Роль системы сформулирована чётко: пост-продажа + операционное сопровождение проблемных активов.
2. Интеграция с ФССП — **корректная** (только мониторинг внешних обременений). Формулировку в docs можно усилить, явно написав: «API используется исключительно для чтения сведений об ИП; закрытие/управление собственными производствами банка через него невозможно и не требуется».
3. Связь с риск-системой — событийная и правильная по разделению ответственности. При желании можно добавить обратный поток (например, события о результате реструктуризации/эскалации) для дообучения моделей, но это уже за рамками текущей версии.
4. Границы, данные и use cases выше можно взять как основу для отдельного документа `00_domain_boundaries_and_use_cases` (на который уже есть ссылки в тексте).
