### Q3 2024 — Сага + идемпотентность
**Спринты 5–10**

**Задачи:**
- Реализация inbox-паттерна для cmd-команд саги (`applyNewTerms`, `closeOldCase`, компенсации).
- Участие в дизайне Camunda-процесса (happy path + compensation).

- Захват/снятие `RestructuringWorkflowLock` (единственный синхронный REST).

- Code review чужих PR.

**Инцидент 1 (существующий в документации)**  
**«Несовместимое изменение поля `overdueAmount`»**  
Кто-то в другом сервисе поменял тип/семантику поля без ревью контракта.  
**Мои задачи по фиксу:**
- Восстановление совместимости (новый `eventType` + миграция consumer-ов).
- Введение обязательного `schemaVersion` + JSON Schema в репозитории.
- Добавление в CI проверки `contract-change` + обязательного ревью владельцев consumer-ов.
- Написание регрессионных contract-тестов.

### Q4 2024 — ФССП + уведомления + эскалация
**Спринты 11–16**

**Задачи:**
- Интеграция `legal-holds-integration-service` (poll ФССП, ACL → доменные события).
- Circuit breaker + bulkhead + rate-limiter.
- `collection-notification-service`: обработка `proposeTerms` / `compensateProposeTerms`.
- Автоматическая эскалация по SLA (старт таймера от `rop.notifications.sent`).
- Метрики Prometheus (inbox success/fail, lock duration, FSSP latency).

**Инцидент 2 (новый)**  
**«FSSP rate-limit + массовый stale»**  
После увеличения частоты poll’ов начали ловить 429 и circuit открывался надолго.  
**Мои задачи по фиксу:**
- Тонкая настройка rate-limiter (Redis) + jitter.
- Улучшение fail-open логики и маркировки `fssp_check_stale`.
- Дашборд + алерт на процент stale-проверок.
- Документация порта `FsspProvider`.

### Q1 2025 — Миграция legacy (начало) + hardening саги
**Спринты 17–22**

**Задачи:**
- `legacy-collection-migration-service`: extract → validate → daily reconciliation.
- Буферизация событий по `aggregateVersion` (межтопиковый порядок).
- Автоматизация сверки (снижение ручной проверки).
- Доработка компенсаций (ретраи до успеха без SLA-таймера).
- Участие в написании OpenAPI + технических дизайнов.

**Инцидент 3 (новый)**  
**«Дублирование процессов реструктуризации»**  
Из-за race при старте процесса + сетевом ретрае фронта иногда создавалось два экземпляра Camunda.  
**Мои задачи по фиксу:**
- Усиление атомарности `INSERT ... ON CONFLICT` лока.
- Фоновая очистка orphaned-локов + запись в audit.
- Интеграционный тест на concurrent start.
- Обновление flowchart для аналитиков.

### Q2 2025 — Масштабирование миграции + Outbox в бою
**Спринты 23–28**

**Задачи:**
- Массовый прогон миграции (цель — десятки тысяч дел).
- Оптимизация reconciliation (классификация MAPPING_ERROR / DATA_DRIFT).
- Transactional Outbox под нагрузкой (к этому моменту уже > 1 млн событий).
- Поддержка auto-escalation (сокращение задержки с суток до минут).
- Регулярные code review и тех-синки.

**Инцидент 4 (новый)**  
**«Outbox lag + потерянные события при рестарте пода»**  
После деплоя с коротким terminationGracePeriod relay-воркер не успевал дослать.  
**Мои задачи по фиксу:**
- Увеличение graceful shutdown + проверка «все outbox-записи published» перед SIGTERM.
- Метрика lag outbox + алерт.
- Идемпотентный consumer на стороне получателей (дополнительная защита).

### Сводка по ключевым результатам разработчика к концу горизонта
- Inbox защитил от повторного выполнения команд.
- Outbox обработал > 1,2 млн событий за 4 месяца пиковой нагрузки.
- Автоэскалация сократила задержку с суток до минут.
- Миграция: > 40 000 дел, ручная проверка упала с ~400 до 15–20 в неделю.
- Все крупные инциденты (схема, FSSP, дубли процессов, outbox lag, память, компенсации) были закрыты с участием разработчика — от диагноза до фикса и регрессионных тестов.

Такой таймлайн реалистичен для банковской команды среднего размера и полностью соответствует описанной архитектуре и статусу проекта.
